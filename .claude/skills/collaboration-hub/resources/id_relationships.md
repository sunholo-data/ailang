# ID Relationships Across AILANG Databases

This document describes how identifiers relate across the three SQLite databases used by AILANG.

## Overview

AILANG uses THREE separate SQLite databases that reference each other through shared IDs:

| Database | Location | Purpose |
|----------|----------|---------|
| **observatory.db** | `~/.ailang/state/observatory.db` | OTEL spans, traces, task/agent hierarchy |
| **coordinator.db** | `~/.ailang/state/coordinator.db` | Task execution state, approvals, events |
| **collaboration.db** | `~/.ailang/state/collaboration.db` | Messages, threads, agents |

## ID Flow Diagram

```
COLLABORATION.DB                    COORDINATOR.DB                     OBSERVATORY.DB
===============                     ==============                     ==============
threads.id ─────────────────────────► tasks.thread_id
     │
messages.id (UUID) ─────────────────► tasks.message_id
     │                                     │
     │                                     ├── tasks.id = "task-" + first_8(message_id)
     │                                     │        │
     │                                     │        └────────────────────► tasks.id (same)
     │                                     │                                    │
     │                                     │   tasks.session_id ◄───────────────│── spans.attributes.session.id
     │                                     │                                    │
     │                                     │                               agent_assignments.id
     │                                     │                                    │
     │                                     │                               spans.id ◄── span_id (16-char hex)
     │                                     │                                    ├── trace_id (32-char hex)
     │                                     │                                    ├── parent_span_id
     │                                     │                                    ├── task_id (FK)
     │                                     │                                    └── agent_assignment_id (FK)
```

## ID Format Reference

| ID Type | Format | Example | Generated By |
|---------|--------|---------|--------------|
| `task_id` | `task-<8-char-uuid>` | `task-29404032` | Coordinator (from message UUID) |
| `message_id` | Full UUID | `29404032-74b3-40c6-acc3-23d6bbe14b68` | Collaboration.db |
| `thread_id` | `thread_<ts>_<rand>` | `thread_1768064360112_5f96886d` | Collaboration.db |
| `workspace_id` | `ws_<16-char-hash>` | `ws_a1b2c3d4e5f67890` | SHA256(workspace_path) |
| `agent_assignment_id` | `aa_<16-char-hash>` | `aa_f1e2d3c4b5a69870` | SHA256(task_id+agent_id+timestamp) |
| `span_id` | 16-char hex | `0f9632b58df815e4` | OTEL SDK |
| `trace_id` | 32-char hex | `0ebf5e64bb654fcc1d19256b59f05ae3` | OTEL SDK |
| `session.id` | UUID | `4df60536-caed-4e2f-af2c-e386c361f4e7` | Claude Code/Gemini CLI |

## ID Generation Details

### Task ID Generation

The coordinator creates task IDs by extracting the first 8 characters of the source message UUID:

```go
// In internal/coordinator/message_adapter.go
taskID := fmt.Sprintf("task-%s", msg.ID[:8])
```

**Example:**
- Message ID: `29404032-74b3-40c6-acc3-23d6bbe14b68`
- Task ID: `task-29404032`

### Workspace ID Generation

Workspace IDs are deterministically generated from the absolute path:

```go
// In internal/coordinator/observatory_sync.go
hash := sha256.Sum256([]byte(absPath))
workspaceID := "ws_" + hex.EncodeToString(hash[:8])
```

### Agent Assignment ID Generation

Assignment IDs include a timestamp to ensure uniqueness:

```go
// In internal/coordinator/observatory_sync.go
data := fmt.Sprintf("%s:%s:%d", taskID, agentID, time.Now().UnixNano())
hash := sha256.Sum256([]byte(data))
assignmentID := "aa_" + hex.EncodeToString(hash[:8])
```

## How Spans Link to Tasks

Spans can be linked to tasks through multiple mechanisms:

1. **Direct FK:** `spans.task_id` directly references the coordinator task
2. **Parent-child:** `spans.parent_span_id` builds tree within a trace_id
3. **Session correlation:** `spans.attributes.session.id` links Claude Code sessions
4. **Assignment linkage:** `spans.agent_assignment_id` links to executing agent

## Span Attributes

Key attributes stored in `spans.attributes` JSON:

| Attribute | Type | Description |
|-----------|------|-------------|
| `session.id` | UUID | Claude Code/Gemini CLI session ID |
| `turn.number` | int | Turn number (for exec.turn spans) |
| `task.id` | string | Coordinator task ID (redundant) |
| `ai.model` | string | Model used for AI operations |
| `ai.provider` | string | Provider (claude, gemini, etc.) |
| `ai.tokens_in` | int | Input tokens for AI calls |
| `ai.tokens_out` | int | Output tokens for AI calls |

## Cross-Database Queries

### Find all data for a task

```bash
# Find task in coordinator
sqlite3 ~/.ailang/state/coordinator.db \
  "SELECT id, message_id, thread_id, session_id FROM tasks WHERE id = 'task-29404032'"

# Find same task in observatory
sqlite3 ~/.ailang/state/observatory.db \
  "SELECT id, workspace_id, source_ref FROM tasks WHERE id = 'task-29404032'"

# Find original message in collaboration
sqlite3 ~/.ailang/state/collaboration.db \
  "SELECT id, thread_id, content FROM messages WHERE id = '29404032-74b3-40c6-acc3-23d6bbe14b68'"
```

### Find spans by session

```bash
# Find all spans with a specific session.id attribute
sqlite3 ~/.ailang/state/observatory.db \
  "SELECT id, name, json_extract(attributes, '\$.turn.number') as turn \
   FROM spans WHERE json_extract(attributes, '\$.session.id') = 'SESSION_UUID'"
```

### Trace lineage for a message

```bash
# 1. Start with message
MSG_ID="29404032-74b3-40c6-acc3-23d6bbe14b68"

# 2. Find task
TASK_ID="task-${MSG_ID:0:8}"

# 3. Find all spans
sqlite3 ~/.ailang/state/observatory.db \
  "SELECT id, name, trace_id FROM spans WHERE task_id = '$TASK_ID'"
```

## Common Pitfalls

### span.task_id May Be NULL

Spans created by CLI tools (Claude Code, Gemini CLI) during tool execution may not have `task_id` set because TRACEPARENT is not propagated through these tools. Use `session.id` attribute for correlation instead.

### Don't Confuse trace_id and task_id

- `trace_id`: OTEL concept - groups spans from a single distributed operation
- `task_id`: AILANG concept - links spans to a coordinator task

A single task can have spans across multiple traces (especially when TRACEPARENT propagation fails).

### Session Correlation is the Most Reliable

When spans are orphaned (no task_id), the `session.id` attribute in `spans.attributes` is the most reliable way to correlate them with the coordinator task's `session_id`.
