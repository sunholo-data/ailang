### Fixed — `check` was exponential on nested record literals and doubling type aliases (#2308, #2329) (2026-11-16)

A ~1 KB program could drive `ailang check`, and with it the LSP and the hosted check tool, to
minutes of CPU or tens of GiB of memory. Each cause is fixed where it arises:

- **Record literals.** A closed record literal carried its fields twice: in `TRecord.Fields` and
  again in an identical `Row`. Every traversal that walks a record therefore visited each field
  twice, so a record nested `n` deep cost `2^n`. Depth 16 took about 15 s; a getter applied to a
  depth-60 literal reached about 50 GiB. A literal's type now has its fields once, as a written
  closed record type does.
- **Information-flow parameter-bound walk.** The walk re-walked a type alias for every path that
  reached it. Affected shapes: a chain of aliases each doubling its argument
  (`type P0[a] = P1[(a, a)]`, ...), a dense DAG of aliases (each a tuple of the previous five),
  and aliases that pass a parameter through (`type Q1[a] = (Q0[a], Q0[a])`). The walk now shares
  repeated work. It numbers each alias argument by its structure, resolved through the parameter
  bindings, so the `a` written separately in each alias body counts as one argument. The memory
  it keeps for one walk is capped.
- **Shared types walked once per path.** The per-application callback scan and the record
  TypeName propagation now visit a shared type, and an expanded alias application, once.
- **Unifying equivalent aliases.** Unifying applications of two separately declared but
  equivalent aliases to the same arguments (`f(x: D119) -> E119`,
  `f(u) -> Q22[int] = g(u)` with `g: int -> P22[int]`) now succeeds at once, because both sides
  expand to the same type. Before, unification expanded every pair once per path.
- **Diagnostics.** A type error through such an alias wrote the fully expanded type into the
  message: ~460 KB at 16 aliases, gigabytes at 30. Diagnostics now render a type of more than
  4,096 nodes in part, with an ellipsis and its size.

### Changed — BREAKING: a type too large to check is an error, TC_TYPE_SIZE_001 (2026-11-16)

As a backstop, `check` now reports `TC_TYPE_SIZE_001` instead of walking the type. The error
also appears in `check --json`. It names the let binding, declaration or exported name, its
position, and the measured size against the limit. It is raised for:

- **A type whose tree exceeds 65,536 nodes.** The largest type in the repository and in the
  14,779 banked solutions is 107 nodes, 612x below the limit.
- **A declaration whose unification takes more than 2^24 steps.** The largest real declaration
  takes 365,050 steps, 46x below. The budget fires after about 7 s.
- **Types nested more than 1,000 deep.** Unification already stopped at that depth, by
  panicking with "unification depth exceeded 1000", which crashed `check`. This was the crash
  #2327 reported; it was still reachable through two written 1,100-deep list types. The deepest
  real type is 10 levels. A long list literal, or a long `::` or `++` chain, is a deep
  expression, not a deep type, and is unaffected.

Programs that checked before and are now rejected:

- **Repeated self-pairs.** A type that repeats a part at every step: `let t1 = (t0, t0)`
  repeated 16 times (131,071 nodes; it checked in 0.1 s), or a doubling alias whose expansion a
  call materialises.
- **Exported dense alias DAGs.** The module interface stores the alias expanded. Such a program
  checked with the compile cache off, but exhausted memory with the cache on, which is the
  default.
- **Wide records nested in records.** A record of 40 fields, each holding the same 40-field
  record, each holding the same 40-field record, built with lets (65,641 nodes; it checked in
  0.8 s and 250 MB). The same holds for 16 or 20 fields nested four deep (69,905 / 168,421
  nodes; 2 s and 4.6 s), 10 fields nested five deep (111,111 nodes; 6 s), and 8 fields nested
  six deep (299,593 nodes; it exhausted 3 GB).

Remedy: give the repeated part a nominal type, a data type such as `type Pair = Pair(T, T)` or
`type Row = Row({...})`, which is never expanded. Or restructure the value so its type does not
hold the same large part many times over.
