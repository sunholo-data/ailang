### Fixed — `check` was exponential on nested record literals and doubling type aliases (#2308, #2329) (2026-11-16)

A ~1 KB program could drive `ailang check` — and so the LSP and the hosted check tool — to minutes
of CPU or tens of GiB of memory. Each cause is fixed where it arises:

- A closed record literal carried its fields twice, in `TRecord.Fields` and again in an identical
  `Row`, so every traversal that walks a record visited each field twice: a record nested `n` deep
  cost `2^n` (depth 16 took ~15 s; a getter applied to a depth-60 literal reached ~50 GiB). A
  literal's type now has its fields once, as a written closed record type does.
- The information-flow parameter-bound walk re-walked a type alias for every path that reached it,
  so a chain of aliases each doubling its argument (`type P0[a] = P1[(a, a)]`, ...) or a dense DAG
  of aliases (each a tuple of the previous five) in a signature took `2^n`. It now shares repeated
  (node, bindings, path) work.
- The per-application callback scan and the record TypeName propagation walked a shared type node
  once per path; each now visits a node once. Unifying two separately declared, structurally equal
  ground aliases (`f(x: D119) -> E119`) unifies each pair of aliases once.

### Changed — BREAKING: a type too large to check is an error, TC_TYPE_SIZE_001 (2026-11-16)

As a backstop, `check` now reports `TC_TYPE_SIZE_001` (also in `check --json`), located at the let
binding, declaration or exported name where it arises, instead of walking:

- a type whose tree exceeds 65,536 nodes — a part repeated at every step (`let t1 = (t0, t0)`
  repeated, a doubling alias whose expansion a call materialises, or an exported dense alias DAG,
  which the module interface stores expanded). The largest type in the repository and the banked
  solutions is 292 nodes;
- a declaration whose unification takes more than 2^26 steps (the largest real declaration takes
  365,050);
- types nested more than 1,000 deep, which made `check` panic with "unification depth exceeded
  1000" (the crash #2327 reported, still reachable through two written 1100-deep list types).

A program that used such a type and checked (slowly, or with the compile cache enabled, by
exhausting memory) is now rejected: wrap the repeated part in a data type, which is never expanded.
