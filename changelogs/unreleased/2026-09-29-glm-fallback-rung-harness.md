### Fixed — mission loops on the pi fallback rung (glm-5.3), 2026-09-28/29 overnight

- **A pi controller is no longer killed while waiting.** pi's bash tool has no default timeout; World iter-208 waited on its codex executor in one 28-minute command, the stall watchdog killed it at 03:11Z, and codex finished `rc=0` six minutes later with the work stranded (salvaged to ailang-world #163). New `tools/pi-extensions/controller-bash-cap.ts` caps each controller command at 540s (`MISSION_PI_BASH_CAP_S`), under the watchdog's 600s window.
- **A pi controller retry resumes instead of dying.** `Provider finish_reason: error` (OpenRouter mid-stream) is now in `TRANSIENT_SIG` — pi's own retry list does not match it — and the controller runs under a fixed `--session-id` per fire, so a retry continues the same session.
- **The controller prompt names the mission-control skill by absolute path.** A relative `.claude/skills/...` does not exist in ailang-world or stapledons-godot; a pi controller went looking with `find ~ -maxdepth 6`, which never returned.
- **Role spawns respect the ration.** The driver exports `MISSION_OVER_RATION`; `resolve-role-spawn.sh` reroutes an over-ration recipe to the driver's resolved lane (`over-ration-reroute:<bucket>`) or refuses it (`refuse over-ration:<bucket>`). World iter-208 had run planner and executor on codex after the driver refused codex as over ration.
- **`mission_pi_run.sh` no longer blames the model for a hung command.** A silent run with a tool call still open is `tool_hang` (rc 18, `hung_tool` in the verdict), not `stream_dead`. All three iter-208 "deepseek stream_dead" verdicts were `ailang messages list` hanging inside the sandbox.
- **One-shot `ailang messages` commands are bounded at 90s** (exit 124 with a diagnosis). With Firestore unreachable, `messages list` previously never returned.
