### Changed — BREAKING: `Json` gains `JInt(int)`; integer JSON numbers are exact (2026-11-10)

JSON numbers were all floats, so an integer above 2^53 was silently changed:
`{"id": 1234567890123456789}` re-encoded as `1234567890123456800`, and `jint(n)` did the same.
`std/json`'s `Json` now has a seventh constructor, `JInt(int)` (declared last, so the other
constructors keep their tags).

- `decode` gives `JInt(n)` for an integer literal that fits int64 (`42`, `-7`,
  `9223372036854775807`), and `JNumber(x)` for everything else: fractions and exponents
  (`1.0`, `1e3`), `-0`, and integers outside int64 (`9223372036854775808`). A literal outside
  float64 range (`1E400`) is still an `Err`.
- `jint(n)` builds `JInt(n)`; `encode` prints a `JInt` digit for digit. `encode` of a `JNumber`
  is unchanged, so output only changes where a value above 2^53 used to be rounded.
- `asNumber`, `getNumber`, `filterNumbers`, `allNumbers` and the `getNumberArray*` family accept
  both constructors (a `JInt` converts to the nearest float).
- `getInt` returns a `JInt`'s value exactly, and an integral `JNumber`'s (`30.0` → `Some(30)`).
  It **no longer truncates**: `1187.50` is `None` (it was `Some(1187)`), and so is a `JNumber`
  outside int64.
- YAML goes through the same decoder, so `yaml.decode` also gives `JInt` for integers.
- `std/sem` writes its integer fields with `jint` (a 64-bit simhash now survives the round trip)
  and `std/jwt`'s integer claims read `JInt`.

**What you will see.** `show` of a decoded integer prints `JInt(1)` where it printed
`JNumber(1.0)`, and `decode("1") == Ok(jnum(1.0))` is now `false` (`decode("1") == Ok(jint(1))`
is `true`). Code that reads numbers through the accessors keeps working. A `match` over `Json`
that has a `JNumber` arm and a catch-all (`_ =>`) still compiles but **sends integers to the
catch-all**; `ailang check` and `ailang run` flag every such match with the transitional warning
`TC_MATCH_005` (stderr, `check --json` `warnings`, `--format agent` `warn:` lines).

**Migrate.** Add a `JInt(i) => …` arm next to each `JNumber(n) => …` arm (use `intToFloat(i)`
if you want a float), or read numbers with `asNumber`/`getNumber`/`getInt`. Replace
`jnum(intToFloat(n))` with `jint(n)`. Design: M4 of
design_docs/planned/v1_0_0/m-v1-stdlib-surface-polish.md (§7, ledger D-66 ruling 4).

### Fixed — BREAKING: `json.decode` accepted trailing data and dropped or scrambled `""` keys (2026-11-10)

`decode("1 2")`, `decode("[1]]")` and `decode("{\"a\":1} xx")` returned `Ok` of the first value;
`decode("01")` returned `Ok(0)`. They are now `Err("decode: trailing data at offset N")`, where
N is the byte offset of the first non-whitespace byte after the value. Whitespace before and
after the value is still allowed. Use `json.repair` for lenient input such as model output with
trailing prose.

An empty-string object key is an ordinary key. The evaluator dropped `{"": 1}`'s key and the VM
kept it; with a string value (`{"": "x", "b": "y"}`) both engines mistook the value for the next
key and produced `{"x": "b"}`. Both now keep `""` and the pairs in order.

There were three hand-copied JSON decoders (the registry builtin, the bytecode VM and a legacy
evaluator copy, the last of which also reordered keys). All three now run one shared token walk
(`eval.DecodeJSON`) and differ only in how they build values, so the number, key and end-of-input
rules cannot drift between engines again. Design: B1, B2 of
design_docs/planned/v1_0_0/m-v1-stdlib-surface-polish.md (§8).

### Added — `TC_MATCH_005`: warning for a `Json` match with a `JNumber` arm and no `JInt` arm (2026-11-10)

Transitional for the v0.58.x window: it turns the silent fall-through described above into a
visible one. Keyed on constructor identity — std/json's `JNumber`, including an aliased import —
so a module's own `JNumber` constructor is never flagged. It looks at every pattern depth
(`Some(JNumber(n))` counts) and every match, including in lambdas. It runs over Core in the module
pipeline, so it is reported on a warm compile cache too. `check --json` gives it a `file` (the
module that holds the match, which may be an imported one), `line`, `column` and `suggestion`.
