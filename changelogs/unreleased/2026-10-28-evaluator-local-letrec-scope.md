### Fixed — A local `letrec` no longer rebinds names in closures made before it (2026-10-28)

The evaluator copied every `letrec` binding into the enclosing environment after evaluating it ("Phase 2.5" in `evalCoreLetRec`). That step exists so a top-level declaration's bindings stay visible to later declarations (the REPL and wasm module registry, `EvalCoreProgram`), but it also ran for a local `letrec` inside a function body. The enclosing environment is the one closures created earlier in the same block had captured, so writing into it rebound their free names to a `letrec` defined after them. With a top-level `func isOdd`, a block `letrec isEven = \k. … isOdd(k - 1); letrec isOdd = …; isEven(7)` made `isEven` call the later local `isOdd` and printed `false`, while the type checker resolves that `isOdd` to the top-level function and the bytecode VM printed `true`. The propagation now applies only to the LetRec handed to `Eval` / `EvalCoreProgram` as a declaration; a nested `letrec` stays lexically scoped, and the evaluator prints `true`. Regression test: `internal/runner/letrec_scope_test.go` (all three engines, plus the type checker rejecting the program when no top-level `isOdd` exists).
