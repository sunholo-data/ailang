### Added — `eval-paired` checks the arms sent the same request (wire parity)

`ailang eval-paired` now reads each arm's OpenRouter Broadcast traces (prod observatory) and compares the request parameters that actually went on the wire: output cap (`max_tokens`/`max_completion_tokens` as one knob), `reasoning`, `provider` routing, sampling, any other non-transport field, and the majority host. A difference is reported as `wire_parity.status: "mismatch"` with a `CONFOUNDED:` warning naming each parameter; no traces is `unverified`, a non-OpenRouter arm `not_applicable`. `--require-wire-parity` exits 3 unless the arms match; `--wire=false` skips the check.

Why: every glm-5.3-flash pi-vs-motoko A/B to date compared two different requests. On 2026-10-16 the traces showed motoko sending `max_tokens: 32000` with the registry's `provider` block and no reasoning effort, while pi sent `max_completion_tokens` ≈ 900k–943k, `reasoning.effort: "high"` and no `provider` block at all — pi's installed `~/.pi/agent/models.json` does not carry the model, so pi used its own catalogue, and AILANG's routing never reaches pi's HTTP client. motoko hit the 32k cap 27 times in the hard-set run; pi never. A call is attributed to an arm only when its task prompt names the arm's eval workdir: agents that list the shared `ailang_eval` parent carry other runs' directory names into tool results.
