### Fixed — Local `letrec` no longer gives a wrong answer on the bytecode VM (2026-10-28)

A local `letrec` whose name was also a top-level function gave a different answer under `ailang run --bytecode` and `--strict-bytecode` than on the evaluator: the self-call bound to the top-level function. `benchmark/shadow.ail` from the design doc printed `10` on the evaluator and `1000` on both VM engines, and the strict gate did not catch it. Local `letrec` now compiles natively on the VM. The lowering marks every binding of a local letrec with its whole group (`stmt.VarDecl.RecGroup`), and the compiler gives each member a prototype that shares one capture list, so a self or mutual reference rebuilds the member's closure from the frame's own captures instead of looking the name up at top level. A self tail call is an `OpTailCall` on that closure, so a 1,000,000-iteration local loop runs in constant VM stack. A letrec binding that is not a lambda, or a letrec the lowering meets in expression position, now makes the enclosing function evaluator-only instead of compiling a guess. Measured over the 41 banked model solutions from the CP spike, strict-VM NATIVE went from 31 to 41, including the 4 that crashed under `--bytecode`. Regression fixture: [`examples/runnable/letrec_local_shadow.ail`](../../examples/runnable/letrec_local_shadow.ail), pinned on all three engines by `internal/runner/vm_letrec_test.go`. Design: [m-vm-coverage-letrec-prelude-bridge](../../design_docs/planned/v0_55_0/m-vm-coverage-letrec-prelude-bridge.md) (G1, G1b).

### Fixed — Module-level values read correctly on the bytecode VM (2026-10-28)

A function that read a module-level value binding, such as `let base = 40 + 1` or `let halfF = 2.0`, failed under `--bytecode` and `--strict-bytecode` with `arith ADD: type mismatch Closure vs Int` (or `Float vs Closure`): the VM read the binding's nullary initialiser as a closure. Compilation succeeded, so the strict gate reported such programs as native, and under `--bytecode` the failure arrived after earlier output, so the run exited 1 on a program that is correct on the evaluator (`examples/runnable/array_basic.ail`). A reference to a value binding now calls its initialiser, and calling a value binding that holds a function calls that function. Module-level bindings cannot carry effects, so the result matches the evaluator; the initialiser is recomputed at each reference rather than cached. `array_basic.ail`, `array_grid.ail` and `module_let_helpers.ail` now run natively. Design: G3.

### Changed — A native function that would hand the bridge an unconvertible value now falls back before it runs (2026-10-28)

The VM↔evaluator bridge cannot carry closures, ADTs from the VM, or user ADTs back from the evaluator. A native function that passed one to an evaluator-only function failed at that call, often after effects had run, so `--bytecode` could not replay the program and exited 1. The compiler now checks each reference from a native function to an evaluator-only one against the callee's static signature, and makes the caller evaluator-only too (to a fixed point) when a parameter or the result may carry such a value, or when the signature is unknown. If that reaches `main`, the whole program runs on the evaluator before anything is printed, and `--strict-bytecode` refuses with a reason naming the edge and the callee's own cause. The check is conservative: an erased or polymorphic type counts as unsafe. Design: G4 safety net (not the type-identity fix).
