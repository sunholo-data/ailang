### Fixed — a `match` with no matching arm is RT002 with a position on both engines; the bytecode VM no longer yields Unit (2026-11-10)

When no arm of a `match` matched, the evaluator failed with an unlocated
`no pattern matched in match expression`, and the bytecode VM had no trap at all: the
match fell off its end and produced **Unit**. Depending on the caller, a VM run then
exited 0 with no output (a non-exhaustive match whose result was returned), or died
later in an unrelated place (`arith ADD: type mismatch Unit vs Int` at the caller's
line) and — without `--strict-bytecode` — re-ran the whole program on the evaluator.

Both engines now raise `RT002` (`errors.MatchFailureError`) with the match's
`file:line:col` and the scrutinee's *shape* only — constructor tag, `empty list`,
`list of N elements`, or a type name, never a payload (scrutinees can be secrets):

```
RT002: no arm matched in match at p1.ail:5:35 (scrutinee constructor: Blue)
```

The VM gets a new `MATCH_FAIL` opcode, emitted by the match lowering wherever the
arms are not closed by an unguarded catch-all (the switch `Default`, a failed guard's
fallback, and the end of the if-chain); the text is byte-identical to the
evaluator's, including inside lambdas. Generated Go (`compile --emit-go`) panics with
the same text. `ailang check` is unchanged. Milestone M0 of
design_docs/planned/v1_0_0/m-v1-match-exhaustiveness.md (#2146).
