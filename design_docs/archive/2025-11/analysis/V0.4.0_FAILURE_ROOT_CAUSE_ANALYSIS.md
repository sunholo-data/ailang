## Category 2: Hard-to-Use Features (31 failures, 22%)

### Definition
Features that **exist in AILANG** but are **unintuitive, verbose, or error-prone** compared to other languages. The prompt can help, but these fundamentally need language improvements.

### 2A. Function Type Syntax (18 failures) ⚠️ **MAJOR ISSUE**

**What**: AILANG doesn't support `func(T) -> U` type syntax - must use lambda values.

**Impact**: 18 failures across multiple benchmarks (list_comprehension, higher_order_functions, pipeline)

**Example**:
```ailang
-- ❌ What models naturally write (from ML/Haskell):
export func filter[a](pred: func(a) -> bool, xs: [a]) -> [a] {
  ...
}

-- ❌ AILANG parser error:
-- PAR_UNEXPECTED_TOKEN: expected ), got ( instead
-- (Can't parse func(a) as a type)

-- ✅ Current AILANG workaround:
export func filter[a](pred: a -> bool, xs: [a]) -> [a] {
  ...
}
-- But models don't know this!

-- 🔧 OR use lambda values (verbose):
let myFilter = \pred. \xs.
  match xs {
    [] => [],
    Cons(x, rest) =>
      if pred(x)
      then Cons(x, myFilter(pred)(rest))
      else myFilter(pred)(rest)
  }
```

**Why Hard-to-Use**:
1. Every other ML-family language supports `(T -> U)` type syntax
2. Prompt says "use lambda values, not type annotations" but doesn't show HOW
3. No clear examples of higher-order function types

**Prompt v0.4.1 Status**: Has section "Higher-Order Functions" but examples use lambda values, not typed functions

**Recommended Fixes**:
- **Short-term (v0.4.2)**: Add explicit "DON'T use func(T) -> U" to Critical Limitations
- **Medium-term (v0.5.0)**: Support `(T -> U)` type syntax in parser (M-DX11)
- **Long-term**: Better type inference to avoid needing annotations

**Fix Difficulty**:
- Prompt: ⭐⭐⭐ Hard (fundamental concept)
- Language: ⭐⭐⭐⭐ Medium-Hard (parser + type system changes)

### 2B. List Pattern Cons Syntax (6 failures)

**What**: AILANG uses `::(h, t)` or `Cons(h, t)`, but models want `h::t` (Haskell style).

**Impact**: 6 failures (deterministic_list_transform, list_operations)

**Example**:
```ailang
-- ❌ What models write (natural from Haskell):
match xs {
  [] => ...,
  x::rest => ...  -- Parse error!
}

-- ✅ AILANG requires:
match xs {
  [] => ...,
  ::(x, rest) => ...  -- Constructor call syntax
}
```

**Why Hard-to-Use**:
1. `::` is an **infix constructor** in Haskell/OCaml
2. AILANG treats it as **prefix constructor** (function call)
3. Two valid forms (`::(h,t)` and `Cons(h,t)`) cause confusion

**v0.4.1 Status**: Documented in examples, but not in Critical Limitations

**Recommended Fixes**:
- **Short-term (v0.4.2)**: Add to Critical Limitations: "NO `x::rest` → use `::(x, rest)`"
- **Long-term (v0.6.0)**: Support infix cons syntax `x :: rest` (M-SYNTAX-SUGAR)

**Fix Difficulty**:
- Prompt: ⭐⭐ Medium
- Language: ⭐⭐⭐ Medium (infix operator support)

---

### 2C. Effect Composition Complexity (4 failures)

**What**: Combining multiple effects in complex ways is verbose and error-prone.

**Impact**: 4 failures (effect_composition, effect_pure_separation)

**Example**:
```ailang
-- Models struggle with:
export func process() -> () ! {IO, FS, Net} {
  let file = readFile("config.json");  -- ! {FS}
  let parsed = parseJson(file);         -- ! {Pure}
  let resp = httpPost(url, parsed);     -- ! {Net}
  println(resp)                         -- ! {IO}
}
-- Which effects propagate where? Not obvious!
```

**Why Hard-to-Use**:
1. Effect propagation rules complex
2. Hard to see which functions need which effects
3. Error messages unclear when effects mismatch

**v0.4.1 Status**: Has Effect System section but examples are basic

**Recommended Fixes**:
- **Short-term (v0.4.2)**: More effect composition examples
- **Long-term (v0.7.0)**: Better effect inference, clearer error messages

**Fix Difficulty**:
- Prompt: ⭐⭐⭐ Hard (complex topic)
- Language: ⭐⭐⭐⭐⭐ Very Hard (effect system improvements)

### 2D. Record Update Syntax (3 failures)

**What**: Record updates work but syntax is unfamiliar.

**Impact**: 3 failures (record_update benchmark)

**Example**:
```ailang
-- ❌ Models write (from JavaScript/TypeScript):
let updated = {...person, age: 31}

-- ❌ Or (from Rust):
let updated = person.update(|p| { p.age = 31 })

-- ✅ AILANG uses (from Elm/Haskell):
let updated = {person | age: 31}
```

**Why Hard-to-Use**:
1. Syntax is correct but unfamiliar to JS/Python developers
2. Not obvious that `|` means "update"
3. Models default to syntax from more popular languages

**v0.4.1 Status**: Documented in Records section with examples

**Recommended Fixes**:
- **Short-term (v0.4.2)**: Add to Common Mistakes with wrong examples
- **Long-term**: No language change needed (syntax is good)

**Fix Difficulty**:
- Prompt: ⭐ Easy (add negative examples)
- Language: N/A (syntax is fine)

## Category 3: Unimplemented Features (15 failures, 10%)

### Definition
Features that **don't exist in AILANG** and are either:
1. **By design** (imperative features AILANG intentionally doesn't support)
2. **Future work** (features planned but not yet implemented)

### 3A. By Design - Imperative Features (8 failures)

**What**: AILANG is **pure functional** - these features will never be added.

| Feature | Failures | Reason Not Supported |
|---------|----------|---------------------|
| **for/while loops** | 3 | Use recursion (design choice) |
| **Mutable variables** | 2 | Pure functional (design choice) |
| **List comprehensions** | 2 | Use map/filter (design choice) |
| **Global state** | 1 | Thread state explicitly (design choice) |

**Example**:
```python
# ❌ Will NEVER be supported (imperative):
for i in range(10):
    print(i)

# ✅ AILANG way (functional):
export func loop(n: int) -> () ! {IO} {
  if n > 10
  then ()
  else {
    print(show(n));
    loop(n + 1)
  }
}
```

**v0.4.1 Status**: Well-documented in Critical Limitations

**Recommended Action**: ✅ No changes needed (already clear)

---

### 3B. Future Work - Advanced Features (7 failures)

**What**: Features that **might be added** in future versions.

| Feature | Failures | AILANG Version | Status |
|---------|----------|----------------|--------|
| **Namespace syntax** | 3 | v0.6.0? | Not planned |
| **Type classes (user-defined)** | 2 | v0.4.0+ (structural reflection) | Deferred |
| **Pattern guards** | 1 | **✅ v0.3.15** | **Implemented!** |
| **Quasiquotes** | 1 | v0.4.0+ | Token exists, not implemented |

**Examples**:
```ailang
-- ❌ Models want (from Haskell):
import qualified Data.List as L
L.map(f, xs)

-- ✅ AILANG doesn't have namespaces (by design)
import std/list (map)
map(f, xs)

-- ❌ Models want (from Haskell):
class Functor f where
  map :: (a -> b) -> f a -> f b

-- ✅ AILANG: Hardcoded type classes in v0.3.x
-- 🔜 AILANG: Structural reflection in v0.4.x+
```

**v0.4.1 Status**: Some documented as limitations, others not mentioned

**Recommended Action**:
- **v0.4.2**: Add "NO namespace syntax" to Critical Limitations
- **Future**: Implement or clarify will never support

## Conclusion

**68% of v0.4.0 failures are prompt-fixable!**

The v0.4.1 prompt we just created addresses 20 failures (JSON/HTTP issues). The next two iterations (v0.4.2, v0.4.3) can address 78 more failures by:
1. Adding explicit anti-patterns
2. Showing negative examples
3. Simplifying complex examples
4. Better documenting existing features

Only **22% of failures** require language changes (hard-to-use features), and **10%** are unimplemented by design.

**Bottom line**: Focus on **prompt improvements first** (v0.4.1-v0.4.3), then consider **language improvements** (v0.5.0+) to maximize AILANG's success rate.
