# Google Search grounding for std/ai Gemini calls

- **Date**: 2026-10-28
- **Class**: feature
- **Recommend**: design-doc
- **Searched**: `googleSearch|google_search|grounding` across `internal/`, `std/`, `design_docs/`, `docs/` — zero hits (report's "no grep hit" verified on the working tree). `ground|search` across `design_docs/` — nearest is `design_docs/deferred/m-gemini-interactions-api.md`, which mentions `google_search` only as a *future* capability of the not-yet-planned Interactions API migration (its line 226 sketch, `Tools: []gemini.Tool{{Type: "google_search"}}`); it does not design grounding on the current `generateContent` surface, so this is not a duplicate.

The mechanism checks out and the plumbing is mostly there: `internal/ai/gemini/types.go` already has the top-level `tools []toolBlock` wire field (`toolBlock` currently carries only `functionDeclarations`, per `internal/ai/gemini/step.go:225` "Tools → top-level functionDeclarations"), so turning on Vertex's built-in tool is extending an existing block with a `googleSearch {}` variant, not new transport. What is genuinely new surface: a `groundingMetadata` path from the Gemini response (`groundingChunks` → uri/title, `groundingQueries`/webSearchQueries) up through the `AIHandler` interface (`internal/effects/ai.go:27`), a new builtin (sibling of `internal/builtins/ai.go` / `ai_image.go`), and public `std/ai.ail` exports (`callGrounded`, grounded image variant, plus `Source {uri,title}` / result record types) under the existing `AI` effect — no `Net`, no credential leak into user code, which is exactly the point for Daneel's `linkedin:propose` row (AI-only by design; `std/web.webSearch` is a different backend, ollama.com via `Net`, confirmed at `std/web.ail:31`).

Why design-doc and not direct-fix: (1) multiple acceptable API shapes — dedicated `callGrounded(model, prompt)` / grounded-images functions vs. an options/capabilities record threaded through the existing `call`/`step` vs. a third pseudo-tool alongside `ToolSchema` — a decision a reviewer could disagree with (rubric row 3); (2) it changes a public stdlib surface and the `AIHandler` effect contract, setting precedent for other provider built-in tools (code execution, URL context) that will want the same hole (row 4); (3) it spans `std/ai.ail`, `internal/builtins`, `internal/effects`, `internal/ai/gemini`, tests and docs (row 5). Worth folding into the doc: how grounding metadata rides `StepResult` vs a dedicated result record, whether grounding is Gemini-only or a provider-portable "sources" concept, and interaction with `m-ai-call-context.md` (a second `AIHandler` extension interface, following the `AIHandlerWithImageRefs` precedent, is the likely shape — that doc already plans to touch the same interface for cancellation).
