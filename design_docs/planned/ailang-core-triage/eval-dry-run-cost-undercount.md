# eval-suite --dry-run cost estimate undercounts ~7x ($1.70 est vs $12.15 billed)

- **Date**: 2026-11-05
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `dry-run cost estimate`, `estimateRunCost`, `reason_tokens`, `prompt token`, `Estimated cost` across `design_docs/` and `internal/`. Found: `implemented/v0_32_0/m-eval-standard-confidence-gating.md` (the doc that *created* the estimator — describes the shipped mechanism, does not rule on revising its basis), `implemented/v0_15_1/m-eval-cost-and-speed-budgets.md` (agent-mode budgets, different surface), `planned/m-eval-reasoning-model-fairness.md` (reasoning tokens as a *measurement fairness* problem in the harness — budgets/truncation/finish_reason, not cost estimation), `planned/m-quota-rationing-routing.md` (provider-quota routing, adjacent but separate). No doc rules on the dry-run estimator's token basis. The backlog (`planned/ailang-core-backlog.md`) has no prior row on this.
- **Estimate**: omitted (design-doc)

**The estimator's two token inputs are both wrong for cloud reasoning lanes, and each failure compounds the other.** The pre-flight estimator is `cmd/ailang/eval_cost_estimate.go` (`estimateRunCostUSDWithMeans`, ~100 LOC, from M-EVAL-STANDARD-CONFIDENCE-GATING). It prices each (model, benchmark) pair as `historical mean input × input price + historical mean output × output price`, falling back to a flat default of **3000 input / 1500 output tokens** when a pair has no history. Measured 2026-11-05 (fine-tune Phase 0 spike, 6 OpenRouter lanes × 51 benchmarks × 3 trials = 918 runs): 150/306 pairs had no history, so half the estimate used a flat default whose input floor is ~10× below the real ~26k-token AILANG teaching prompt — the single dominant cost driver the report names. Meanwhile even the *history-backed* pairs undercount output: `loadBenchmarkTokenMeans` sums `r.OutputTokens` only, but OpenRouter bills hidden reasoning tokens separately, and qwen3.8-27b alone metered **$7.20 of the $12.15 actual** against an estimate built on 0.07M banked output tokens. Result: $1.70 estimated vs $12.15 billed (~7×).

**What already exists that the design doc should build on.** The harness *banking* side is not the gap: `RunMetrics.ReasonTokens` (`internal/eval_harness/metrics.go`, `json:"reason_tokens,omitempty"`) is already captured and banked for standard rows, and the agent path already prices it correctly — `CalculateCostWithCache(lookupKey, result.InputTokens, result.OutputTokens+result.ReasonTokens, …)` in `internal/eval_harness/agent_runner_multi.go`. So part (b) is mostly an estimator-side change (sum `OutputTokens + ReasonTokens` in `loadBenchmarkTokenMeans`; and for no-history pairs, a per-model reasoning multiplier), not new telemetry. Part (a) is the real design question.

**Decisions to rule on.**

1. **Prompt-token basis for no-history pairs (part a).** Options: (i) compute the token count of the actual prompt template per benchmark (correct in principle, but tokenization differs per model — one shared count is itself an approximation); (ii) keep a flat default but recalibrate it to a measured prompt-plus-task figure (one-line-ish, but fails again for the next prompt revision); (iii) seed means from any completed run on the same benchmark regardless of baseline status. These have different maintenance costs and different accuracy ceilings — a reviewer could reasonably pick any.
2. **Reasoning-token accounting for no-history pairs (part b).** Options: (i) a `reasoning_multiplier` (or explicit reasoning budget) column in `internal/modelreg/models.yml` per model — but that changes the models.yml schema, a file-format surface; (ii) use historical `reason_tokens` means where banked history exists and a roster-level default where it doesn't; (iii) treat reasoning models as unpriceable and refuse to estimate (the "no silent fallbacks" hard line argues for loud, not guessy). Each trades schema surface against estimate honesty.
3. **Whether history-backed pairs should also be re-based.** Even with history, per-benchmark means are averaged *across models* (`loadBenchmarkTokenMeans` sums over all standard rows), so a 27B reasoning lane is priced on a mean contaminated by 8B non-reasoning lanes. Fixing only the flat default leaves the biggest lane (qwen3.8-27b, $7.20) still undercounted.
4. **Relationship to `--budget-usd`.** The Phase 0 doc (`planned/v1_1_0/m-eval-finetuning-data-pipeline.md`, §2026-11-05 Phase 0 results) records that the $8 cap did not stop dispatch — that half is already fixed in commit `74857f3c7`. This report is solely about the *estimate*; the design doc should say so explicitly so the cap fix is not re-litigated.

**Why not direct-fix.** The tempting minimal patch — bump the flat defaults and add `+ r.ReasonTokens` in `loadBenchmarkTokenMeans` — is 2–3 lines in one file, but it does not survive contact with decision 2 (no-history reasoning models need a per-model signal that models.yml does not currently carry) and decision 3 (per-model vs per-benchmark means is a schema change to the means lookup itself). Three defensible designs exist; that is row 3 of the rubric, and the schema touch in decision 2(i) is a file-format change (row 4). The estimator is the instrument the program uses to approve real spend — its accuracy contract deserves a reviewed decision, not a defaulted constant.

**Suggested next step.** Fold this into a short design doc (candidate: `m-eval-dry-run-cost-estimate-v2`) rather than a new program lane; cite the Phase 0 measured pair ($1.70 → $12.15, qwen3.8-27b $7.20 @ 0.07M reported output tokens) as the calibration target, and `planned/m-eval-reasoning-model-fairness.md` as the adjacent doc for reasoning-token semantics at the provider boundary.
