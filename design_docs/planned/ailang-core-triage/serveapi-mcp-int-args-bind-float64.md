# serve-api: MCP tools/call binds every JSON number as float64 — int params always fail ("expected float arguments")

- **Date**: 2026-10-07
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `grep -rli "mcp" design_docs/`, `grep -rln "CallPreserveFloats" design_docs/`, `grep -rln "float64" design_docs/planned/ailang-core-triage/`, backlog scan of `design_docs/planned/ailang-core-triage/` (incl. `serveapi-protocol-mcp-dispatch.md`, `serve-api-port-collision.md`); found `design_docs/implemented/v0_9_5/m-serve-api-zero-value-padding.md` — covers the *omitted-param* half of the 39dd37990 family (typed zero binding), but nothing rules on typed binding of *present* numeric args. none found for the present-arg number binding.
- **Estimate**: omitted — recommendation is `design-doc` (rubric rows 4, 5 and 6 all fire). Rough scope: ~150–250 lines across `internal/apiserver/` (binder + its three call sites) plus parity tests on MCP and REST.

Mechanism confirmed in this worktree. `internal/apiserver/mcp.go` (`makeToolHandler`) unmarshals the tools/call arguments into `map[string]any` — every JSON number becomes `float64` — and passes those raw values to `engine.CallPreserveFloats` (mcp.go:452). `CallPreserveFloats` (`internal/embed/embed.go`) exists precisely to keep `float64` as `FloatValue` "even for whole numbers", so a param declared `int` receives a `FloatValue` and the call fails; the literal "expected float arguments" is the evaluator's numeric builtin dispatch rejecting the mixed `(FloatValue, IntValue)` operand pair (`internal/eval/eval_patterns.go`, e.g. for `n * 2`), wrapped by the mcp.go:454 `"function call failed: %v"` prefix. REST is fine because `routes_dispatch.go` (comment block at ~:138) deliberately calls `engine.Call` instead, whose `FromGo` converts whole-number `float64` → `IntValue` (regression-tested as `TestFromGoWholeFloatBecomesInt`, `internal/embed/embed_test.go`) — REST fixed this exact class in one call site and left MCP on the other. Two more MCP-family call sites share the latent bug: `internal/apiserver/a2a.go:226` and `internal/apiserver/mcp_ui_serve.go:103`, both `CallPreserveFloats` on raw JSON-decoded args.

Why not a one-line swap to `Call` (and why this is a design doc): `Call`/`FromGo` converts *any* whole float64 to int, so the opposite case breaks — a `float`-typed param receiving JSON `{"x": 2}` would bind `IntValue` and fail as "expected int arguments". That asymmetry is exactly why MCP chose `CallPreserveFloats` (the mcp.go comment "preserve floats — JSON has no int/float distinction" records the intent). The correct fix is the report's ask: ONE argument binder typed by the declared `ExportInfo.ParamTypes` (which both surfaces already carry), used by MCP tools/call, A2A, MCP UI serve, and REST; int accepts integral numbers only (2.5 → structured invalid-argument error, a deliberate public-surface behavior change), float accepts any number, and omitted `@optional` params bind via the existing `param_zero` machinery (`internal/apiserver/param_zero.go`) — which already does declared-type zeros and just needs to be the shared entry point. Two design-doc triggers beyond size: (1) rubric row 4 — rejecting non-integral numbers for `int` changes behavior of a published MCP/REST/A2A surface (today it's an opaque eval error; tomorrow a typed 4xx-class argument error), and the binder becomes the contract both protocols share; (2) rubric row 3 — at least two viable loci (declared-type-aware conversion inside the engine's arg conversion vs. a binder in `internal/apiserver` that pre-converts before a single `Call` entry point), and the choice determines whether `CallPreserveFloats` survives at all.

Routing: `design-doc-creator`, then sprint-planner. Parity tests must cover: int param with whole number (MCP + REST), float param with whole number (the case `CallPreserveFloats` was protecting), non-integral number for int (reject on both surfaces), bool/string/record/list params, and `@optional` int omitted on MCP binding zero.
