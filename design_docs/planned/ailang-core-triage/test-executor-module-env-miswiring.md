# `ailang test` evaluates through a hand-built evaluator env that diverges from `ailang run` — mis-wired closures across module paths

- **Date**: 2026-09-18
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `injectModuleBindings`, `CombinedResolver`, `test executor`, `executor_helpers` across design_docs/ (hits only in implemented docs for the original harness builds: M-TESTING-DEPS, M-DX25 inline-tests-import-resolution, m-motoko-inline-test-harness, m-testing-adt-import-resolution, m-testing-inline-core-evaluation — none rules on replacing the flat re-injection); `ailang test` + `parity`/`run vs`/`same pipeline` in design_docs/planned/ (hits: m-package-test-discovery — discovery unification only, not evaluation; m-named-test-body-check-semantics / m-named-test-assert-lowering — assert lowering, not env wiring; m-forall-properties-direct-core-eval — forall properties, unrelated); `UnitValue`, `arity`, `mis-wir`, `re-inject` in the backlog — none found. The sibling triage `named-test-float-dict-resolution.md` (#1259) is a *different* defect in the same file (body re-printing / dict resolution), not a duplicate.
- **Estimate**: omitted (design-doc)

The report is precise and the mechanism is verifiable in the tree: `EvaluateNamedTestBodyExprs` (internal/testing/executor.go) builds its own evaluator after the pipeline — `injectModuleBindings` (internal/testing/executor_helpers.go) + `CombinedResolver{Modules: e.modules}` + `injectADTConstructors` — with `e.modules` cached across test bodies (executor.go ~322), a path `ailang run` never takes. `injectModuleBindings`'s own header documents the exact collision class the report hits: bare-name last-writer-wins between modules, patched for LetRec/IndirectValue and VarGlobal re-exports but with bare-name `env.Set(d.Name, funcVal)` still unconditional for non-recursive lambdas under sorted-path order. That explains the signature (a call resolving to a same-named/differently-wired function of another arity; a parameter reading as `UnitValue` from a corrupted closure env) and why renaming everything, a minimal diamond, and inlining as `pure func` change nothing while one private `decode`-ing helper flips previously-green tests. The proposal — evaluate the synthesized test module through the same pipeline + module environment as `ailang run`, plus a parity test diffing both engines per `*_test.ail` body — is the right shape, but it is row 3 and row 5, not a direct fix: there are at least two acceptable remedies (finish the qualified-name-only discipline inside `injectModuleBindings` vs. delete the flat re-injection and reuse the run path wholesale, with the caching of `e.modules` as its own decision), it spans executor.go, executor_helpers.go, the package-test entry in cmd/ailang, and a new parity test, and it changes the test harness's evaluation contract (row 4) for the third time this file has needed surgery (M-DX25, #1259, this).

Two aggravating facts for the design doc to weigh: (1) the report names billing-entitlements at 35/41 failing under `ailang test --package` as likely the same class, so the blast radius is real packages whose suite-wide failures are currently counted as attested by the package-quality ladder — a false negative the harness itself launders; (2) `e.modules` caching across test bodies means one test's pipeline result contaminates the env every later test evaluates in, which is a plausible mechanism for order-dependent failures the report's nil-pointer panic hints at. Related prior art to consult: `m-completion-path-parity` (parity-test pattern) and the M-DX25 doc for why the flat injection exists at all. The #1259 body-re-print defect should be fixed in the same design pass, since both live in the synthesized-module construction and any parity harness would catch both.
