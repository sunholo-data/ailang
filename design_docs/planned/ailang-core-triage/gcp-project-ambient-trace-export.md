# GOOGLE_CLOUD_PROJECT alone switches on Cloud Trace export for every ailang command

- **Date**: 2026-09-30
- **Class**: bug (privacy-adjacent: ambient data egress of fs.path attribute values to a GCP project the user never chose for telemetry)
- **Recommend**: design-doc
- **Searched**: `GOOGLE_CLOUD_PROJECT` (code + design_docs), `Cloud Trace`, `cloudtrace`, `telemetry`, `trace-tier`, `M-PERF6B`, `AILANG_TRACE`; `ls design_docs/planned/` and the ailang-core-triage/ backlog. No existing design doc rules on the export-enablement switch; the closest hits are `m-v1-simplification-program.md` (cloud project *resolution* precedence, not trace export) and M-PERF6B/M-OBS-TRACE-TRIAGE (span *collection* cost/tier, comments in `internal/runner/run.go` — the M-PERF6B comment even says "don't auto-enable on GOOGLE_CLOUD_PROJECT alone", but only governs the run's span collector, not the SDK exporter registration).
- **Estimate**: n/a (design-doc)

## Why

Every `cmd/ailang` entry point calls `otelplatform.Init*` at startup, and `InitWithStatus` registers the Cloud Trace exporter whenever `telemetry.GoogleCloudProject() != ""`. That function is `internal/config/cloud.go` (`TraceProjectFromEnv`): `OTLP_GOOGLE_CLOUD_PROJECT`, falling straight through to plain `GOOGLE_CLOUD_PROJECT` — the generic gcloud/ADC variable most GCP users already have set. The enablement contract is documented and test-pinned (`internal/telemetry/config_test.go` asserts `IsGoogleCloudEnabled()` is true with only `GOOGLE_CLOUD_PROJECT` set; `internal/telemetry/doc.go` and the `cloudVars` table list it as the switch), so this is a designed behavior, not an accidental one — which is exactly why it needs a design doc to reverse: it changes public surface (env-var semantics), affects Cloud Run/GKE deployments where GOOGLE_CLOUD_PROJECT is set *by the platform*, and the fix has multiple defensible shapes the report itself lists (telemetry-only var vs `AILANG_TRACE=gcp` vs `--trace` flag; precedence for an explicit off switch).

Verified sub-findings against the code:

1. **Ambient on-switch confirmed** — `internal/config/cloud.go` (`TraceProjectFromEnv`): the docstring correctly refuses the config-file/metadata fallbacks ("falling through would switch trace export on for every process on a GCE box"), yet still falls through to `GOOGLE_CLOUD_PROJECT`, which has the same ambient quality. `cmd/ailang/main_run_exec.go` even comments "traces exported if GOOGLE_CLOUD_PROJECT ... set".
2. **No visibility under --quiet confirmed** — `Init`/`InitWithStatus` return a status but the `ailang run` path uses `legacyInitialization`, which logs only warnings; no one-liner naming the target project is printed when export activates. The run's own trace notice ("Trace: standard ...") is suppressed under `--quiet` and says nothing about *export* in any case.
3. **Off switch partially exists** — `AILANG_TRACE=off` / `--trace-tier off` / `AILANG_NO_TRACE=1` already stop span *collection* (`internal/runner/run.go`, M-OBS-TRACE-TRIAGE path), and with no collector attached a plain `ailang run` produces no spans to export. But that is collection-tier semantics, not an export kill-switch: anything the platform-side provider instruments independently (AI-call otelhttp spans, future SDK spans) still flows to the exporter. The design doc should define `AILANG_TRACE=off` (or equivalent) as winning over the export decision too.
4. **fs.path always in clear** — `internal/telemetry/effect_spans.go` (`enrichPreCall`, FS case) sets `fs.path` unconditionally; the existing redaction mechanism `AILANG_TRACE_VALUES=off` (`internal/trace/options.go` `ResolveValueMode`) governs the collector's call-tree values and does not touch effect-span attributes (no ValueMode reference in effect_spans.go). Since paths are the sensitive payload (this report's own audit incident), default redaction/hashing belongs in the same design doc — it is a semantics change to recorded span data, so not a free two-liner either.
5. **Deprecated exporter confirmed** — `internal/platform/otel/sdk.go` (`cloudExporter`) uses `github.com/GoogleCloudPlatform/opentelemetry-operations-go/exporter/trace v1.38.0` (archived Cloud Trace exporter, EOL after 2027-01-01). `go.mod` already ships `otlptracehttp` v1.47.0 for the OTLP path, so the migration is mostly configuration (endpoint/project mapping, ADC auth) rather than a new dependency.

Suggested scope for the design doc: (a) redefine the export enablement contract (which vars, precedence, explicit off) across `internal/config`, `internal/telemetry`, `internal/platform/otel` and update the pinned tests + docs; (b) startup notice naming the destination even under `--quiet`; (c) default treatment of `fs.path`/`net.url`/`process.command` attribute values in effect spans; (d) cloudtrace→OTLP exporter migration. Items (a)+(b) are the incident fix; (c) and (d) can be staged or split if the reviewer wants a smaller doc.
