# Dogfood: numerics stdlib gaps (softmax regression, 500x vs DuckDB)

- **Date**: 2026-09-27
- **Class**: feature
- **Recommend**: design-doc
- **Searched**: `iota`, `range` (stdlib), `FloatArray`, `axpy`, `BLAS`, `dot product`, `vector type`, `Arrow`, `columnar`, `mutable`, `in-place` across `design_docs/`; `std/list.ail`, `std/array.ail`, `std/iter.ail` read directly. None found. Nearest relative is `m-list-cons-cells-decomposition.md` / `m-list-repr-spike.md` (planned), but those govern the *internal* list representation (cons-cell Θ(n²) prepend), not the stdlib numeric API surface this report asks for.
- **Estimate**: ~300–800 lines across `std/`, `internal/builtins/`, possibly `internal/effects/` — far past the direct-fix threshold; new public surface and semantics.

One paragraph (why): A dogfooded softmax regression over 768-dim embeddings (5 classes, plain SGD, 74%/65% train/test) works correctly in AILANG but runs at ~10 µs per float op vs ~20 ns in DuckDB (~500x), and the report locates four structural causes, each verified by reading the stdlib: (1) no `range`/`iota` in `std/list`/`std/iter`/`std/array`/`std/math` (grep confirmed — `std/list.ail` documents map/filter/foldl as the O(n) idiom but there is no source list to start from), (2) `std/array.ail`'s `set` is documented copy-on-write O(n) (`std/array.ail:72`), making the canonical accumulator loop Θ(n²) and defeating the module's own "performance-critical" charter, (3) no vector primitives (dot/axpy/scale) so `foldl(+, 0.0, zipWith(*, a, b))` allocates a fresh 768-element intermediate per dot — the allocation traffic, not arithmetic, dominates the 10 µs/op, and (4) JSON is the only numeric ingest (14.4 s to decode 19 MB / 1,252×768 floats) with no binary/columnar path. This is four related stdlib/runtime features, each changing public surface and semantics (new stdlib module functions, possibly a new `Vec`/`FloatArray` builtin type with evaluator and capability treatment, possibly a mutable-array effect, a new binary data format) — textbook row 3/4, design-doc, not direct-fix. Item (a) alone (`range`/`iota` in `std/list`) is the cheap wedge (~20 lines in `std/list.ail` plus builtins and tests) and is the one part that could be split out as a direct-fix if the design doc wants a fast first win; item (b) is the one with the headline 500× payoff. The report's own conclusion — AILANG as typed/effect-checked shell around a columnar engine, numerics in the engine — is consistent with `design_docs/PROGRAM.md`'s positioning and worth carrying into the doc as the framing constraint, so the design decision is really "how far does the small-scale-numerics story go" (stdlib Vec vs leaning harder on embedded DuckDB), which is exactly the kind of ruling a doc exists to settle.
