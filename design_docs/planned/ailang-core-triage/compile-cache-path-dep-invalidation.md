# Compile cache not invalidated when a PATH dependency's interface changes

- **Date**: 2026-09-15
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `cache` across `design_docs/` (M-INCREMENTAL-TYPECHECK, M-PKG-LOCK-PORTABILITY, M-PKG-TRANSITIVE-LOCK-FIX read), `compile cache|cache/compile` in `internal/`/`cmd/`, `content changed` in `internal/pkg/lockfile.go`
- **Why not direct-fix**: The mechanism is confirmed in this repo. `prepareCacheLookup` (`internal/pipeline/pipeline_module_cache.go`) builds `depDigests` only from deps whose CompileUnit is present in `st.compiledUnits` with a non-nil `Iface` — deps served through the package PATH (e.g. `pkg/sunholo/daneel_ext_abi/types`) do not land there, so their interface digest is absent from the `ModuleCacheKey` (`internal/pipeline/cache_key.go`), and a cached 13-field iface is served after the dependency bumps to 14 fields. `ailang lock` detects the drift (`internal/pkg/lockfile.go` `content changed`) but the compile cache never sees it. Reproduced symmetrically on v0.38.5 (daneel 74eb5f3 vs v0.2.0).

  It is a design-doc, not a direct fix, for two rubric reasons. First, the report itself names two acceptable remedies — key the cache on the dependency interface hash the lock already computes, or invalidate entries when lock reports a changed dependency — which is row 3 (more than one acceptable way; someone could reasonably choose either, and they have different trade-offs: keying is self-healing but needs the dep digest plumbed into `prepareCacheLookup` for PATH deps; lock-driven invalidation is simpler but leaves non-lock flows broken). Second, the fix plausibly spans more than one file (`pipeline_module_cache.go` + the loader/PATH-dep resolution path, or `lockfile.go` + cache store) and exceeds the 2-line direct-fix threshold. Prior art: `design_docs/implemented/v0_11_2/m-incremental-typecheck.md` established the cache-key contract but does not cover PATH-dep digests; nothing found rules on this gap.
