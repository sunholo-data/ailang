# std/ai: Gemini file-slicing controls (file/document media parts, page_options, resolution, content_layers)

- **Class**: feature
- **Recommend**: design-doc
- **Searched**: `slicing`, `page_options`, `content_layers`, `Files API`, `file URI` across design_docs/ and std/ internal/ — no doc rules on media parts beyond images or server-side slicing. Nearest neighbours, neither a duplicate:
  - `design_docs/planned/ailang-core-triage/gemini-vertex-regional-host.md` — covers the *adjacent* EU-residency bug (Vertex global host accepts any location segment; regional host swap needed). The requester's item 3 (Vertex regional/EU multi-region endpoints) rides on that fix but that doc says nothing about slicing or media parts.
  - `design_docs/planned/m-ai-call-context.md` — covers cancellable/deadline-carrying AI calls, not message shape.
  - `implemented/v0_30_0/m-gemini-exec-project-plumbing.md` — project/location plumbing only, pins `location = "global"`.

Gap verified against current code: `std/ai/streaming.ail` exposes only string-prompt calls (`call`, `callJson`); the sole structured media path is `[ImagePart]` (`{source, mime}`) on image-ref ops (`internal/effects/ai_image.go`, `AI.callImageWithRefs`) — no file-URI part type, no per-part resolution, no slicing options anywhere in `internal/ai/gemini/`. The report's claims about the surface are accurate.

One paragraph of reason: this adds a new public media-part type and a new options vocabulary (page/sheet/AV slicing, content_layers, resolution) to `std/ai`, threads it through the AI effect handler ops, and teaches the Gemini (and eventually Vertex) provider clients to emit Google's slicing request fields — a semantics-bearing public surface change spanning `std/ai/`, `internal/effects/ai*.go`, and `internal/ai/gemini/` (plus usage-metadata plumbing for metering). There are also genuine open decisions a design doc must settle before code: (a) generalise `ImagePart` into a unified `MediaPart` vs. add a sibling `DocumentPart` type; (b) whether slicing options attach per-part or per-call; (c) which transport the slicing fields ride on first (Developer API `generateContent` vs `/v1beta/interactions` vs Vertex — Google has not wired `page_options` everywhere yet, so the doc should stage rollout and keep the EU-residency requirement from the regional-host triage in view); (d) how usage metadata (`input_tokens`/`output_tokens` on sliced calls) surfaces to AILANG callers. The dogfooding constraint in the report (no raw `std/net` bypass of `std/ai`) is the right instinct and reinforces routing this through the AI effect rather than a workaround. Downstream consumer: DocParse's `pdfBackend=ai` (upload once, slice 1 page/call) and new `pdfBackend=hybrid` (poppler on text-layer pages, sliced AI OCR only on `textlessPages`) per `sunholo-data/docparse/design_docs/planned/gemini_file_slicing_ai_parsing.md` (not in this repo).

Note for the design-doc author: cite `gemini-vertex-regional-host.md` as a dependency for item 3 — until the client honours regional hosts, sliced calls on Vertex would silently route through the global host and EU residency would be illusory again, repeating the measured failure in that triage.
