- **Recommend**: design-doc (all four items individually; see per-item verdicts)

No doc rules on any of the four.
- **Estimate**: omitted (design-doc)

**Item 1 — `show()` truncation producing round-trippable-looking output. Verified in code.** `internal/builtins/show.go`: `showSequence` builds the fully closed `[...]` string and then `truncateIfNeeded` (constants `maxWidth = 80`, `elisionPrefix/Suffix = 20`) replaces the middle with `...`, leaving opening AND closing brackets intact — so the elided output is syntactically indistinguishable from a complete value at every layer except byte count, and `show` is documented as the "canonical string form" (metadata `LongDesc`). A consumer parsing it as JSON gets a truncated array that fails only if the truncation happens to cut mid-token — in the reported case it parsed. The reporter offers three acceptable remedies (never truncate; add `showFull`/`repr`; make truncation visibly invalid, e.g. unterminated bracket) — that is row 3 by definition, and any remedy that changes `show`'s contract or adds a sibling builtin is a public-surface decision (row 4). Note the just-implemented `design_docs/implemented/v0_47_0/m-numerics-vec-array-ingest.md` lists "show truncation length" in its Deferred Decisions, and the show-divergence class (depth/width caps) was already touched by PR #822 — the design doc should reconcile with both. A design doc is warranted despite the small-looking diff, because the choice (silence vs. loudness vs. a second function) is exactly a semantics decision someone could disagree with, and golden fixtures across run/compile backends are affected.

**Item 2 — float-vector ingest without a `Json` tree in between. Feature, design-doc.** The packed codecs this report asks to reuse already landed: `internal/builtins/float_codec.go` registers `_embedding_encode`, `_vec_encode_f64le`, `_vec_decode_f32le/f64le`, and the M6 `Array[float]` pair `_array_encode/decode_f32le/f64le` (M-NUMERICS Phase 0/D4), and `std/json.ail` exposes `decodeFloatArray`. What does not exist is a path-level ingest: `std/fs.readFileBytes` returns **base64 text**, not `bytes` — the implemented doc states this explicitly ("A binary load is therefore read → fromBase64 → decodeF64LE … A direct bytes reader would be a separate `std/fs` change", Implementation Record §5), so this report is the follow-on that deferred sentence anticipated, not a duplicate. Open decisions worth a doc: the surface (`readFloatVectors(path) -> [[float]]` vs. a `readFileBytesRaw` that returns real `bytes` for the existing decoders), the file format DuckDB would emit (one packed vector per file? a header with row-length? line-delimited records), f32-vs-f64 defaulting and its lossiness contract, error semantics for ragged rows, and VM/bytecode bridge coverage (the M6 record shows every ship gate came down to a bridge tag). The reporter's 2.8× finding (per-line decode: 1.50 GB vs 4.19 GB peak on the same data) is a documentation change, not a builtin — fold "decode per line, don't hold one giant tree" into the std/json or std/embedding docs as a milestone of the same doc rather than dispatching it separately. The residual 45× boxing ceiling on `[float]` is the general list-representation problem already owned by `design_docs/planned/m-list-cons-cells-decomposition.md` / `m-list-repr-spike.md` — cite, do not re-open here; the narrow ingest fix stands on its own.

**Item 3 — `ailang docs` prints stale-stdlib content without the mismatch warning. Verified in code.** `cmd/ailang/docs.go` resolves the root via `stdlibroot.Resolve("")` and reads modules from it, but never calls the version check that `ailang run` performs (`internal/loader/stdlib_resolver.go`, `checkStdlibVersion`, comparing the root's `VERSION` file against the binary's base semver, which produced the "stdlib version mismatch: expected v0.47.0, found v0.41.0" line that saved this user from filing a false bug). The check is a private method on `StdlibResolver` with a private `expectedVersion` field, so the fix is a small refactor (expose the check on `internal/stdlibroot` or as a free function) plus the call in `docs.go` — order of 10–15 lines. That exceeds the direct-fix thresholds (2 lines), so row 6 applies: design-doc, though the doc should be a thin one; the only real decisions are warning-vs-error parity with `run`'s `--strict` flag and whether `--all-functions`/`--list` inherit the same warning.

**Item 4 — darwin.arm64 release tarball binary SIGKILLs (137) after `cp` into place.** `code sign` state is the confirmed axis: `codesign --force --sign -` fixes it permanently, which on Apple Silicon means the shipped image's ad-hoc signature is absent or invalid (`SIGKILL`, no diagnostic, is the classic invalid-signature kill). The release workflow (`.github/workflows/release.yml`, `build-release`) builds `darwin/arm64` **natively** on a `macos-latest` runner with plain `go build -ldflags "-X …"`, where the Go linker normally ad-hoc signs — so the precise invalidation mechanism (ldflags interaction, runner toolchain, archive round-trip) needs one diagnosis pass against the actual v0.47.0 artifact before choosing between the three acceptable remedies: (a) sign/verify explicitly in CI (`codesign --force --sign -` + `codesign -v` as a release gate), (b) `codesign` in `docs/static/install.sh` for darwin targets, (c) a documented manual step beside the README's wget+tar+mv install path. Multiple remedies spanning `.github/workflows/release.yml` + installer + docs (rows 3 and 5) → design-doc. Related but not a duplicate: `ailang-core-triage/daemon-liveness-binary-rebuild.md` covers codesign *invalidation of a running image* on rebuild; this is the *shipped artifact* being unsigned/invalid — the shared mechanism (ad-hoc signature discipline) should be noted in one doc covering both, since the daemon triage already established that a broken ad-hoc signature kills silently with zero output.
