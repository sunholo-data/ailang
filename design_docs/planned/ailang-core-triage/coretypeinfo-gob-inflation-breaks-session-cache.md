# Compile cache rejects motoko `session.ail`: CoreTypeInfo blob grew past the 64 MiB ceiling (~2 min recompile on every motoko start)

- **Date**: 2026-10-12
- **Class**: bug (performance regression)
- **Recommend**: design-doc
- **Searched**: `maxArtifactBlobBytes`, `ARTIFACT_TOO_LARGE`, `coretypeinfo`, `CoreTypeInfo` across `design_docs/`; found `ailang-core-triage/inline-test-per-case-recompile-1328.md` (which covers the earlier 16→64 MiB ceiling raise in #1328 and already documents the no-sharing encoding problem) but no doc ruling on this new regression; `ailang-core-backlog.md` has no row for it.
- **Estimate**: n/a (bisection across ~181 commits, an encoding redesign in `internal/types`/`internal/pipeline`, and a new guard test — far beyond direct-fix scale)

The report is credible and reproducible in mechanism. `session.ail` is unchanged since 2026-09-21, yet on 2026-10-08 (build `5ab23e8`) its `coretypeinfo.gob` was 29.3 MB — under the ceiling — while today's v0.54.5/v0.54.6 builds exceed the 64 MiB `maxArtifactBlobBytes` limit (`internal/pipeline/cache_artifacts.go:33`), so `CACHE_WRITE_FAILED ... ARTIFACT_TOO_LARGE` fires on every motoko start and every run pays a 70–130 s recompile. Bisecting the ~181 commits in that window, the prime suspect is **accdfc4bf** ("Repair shared effect rows at App constraints and publication", M-EFFECT-ROW-VAR-UNIFICATION, #616, merged 2026-10-09): it replaced `ctx.freshEffectRow()` at App/Lambda sites with `applicationEffectRow(fnType)`, added `ImplicitEffectContract`, and publishes a materialized `ApplicationEffects` record (CallRow with labels, params, budgets, open tails) per App node — exactly the kind of per-node duplication that inflates CoreTypeInfo. Secondary suspect: **3c0d5d8bf** (recursive row alias resolution, 2026-10-10), which expands row aliases in `row_unification.go`. Both postdate 5ab23e8 and precede v0.54.5, matching the timing.

Root cause is structural, not the ceiling: CoreTypeInfo is `map[uint64]Type` gob-encoded with each node's type stored independently; the addendum of `inline-test-per-case-recompile-1328.md` already measured ~11,639 entries collapsing to ~996 distinct types for a comparable module, i.e. deduplication/interning of types at encode time (keyed by each type's own gob bytes) would cut the blob several-fold and make the cache robust without raising the ceiling again. Caveat to check in a design doc: decoded types would then share pointers, so consumers must be verified not to mutate CoreTypeInfo types in place.

Recommend a design doc covering: (1) empirical bisect confirmation (build `ailang check` against session.ail at candidate commits and measure encoded gob size), (2) type sharing/interning in the CoreTypeInfo encoder, (3) a guard test asserting a large real-world or synthetic module stays under `maxArtifactBlobBytes`, so silent recurrence is caught in CI.
