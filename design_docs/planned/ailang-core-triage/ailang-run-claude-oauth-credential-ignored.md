# `ailang run -ai claude-opus-5` can never use the Claude OAuth credential the factory already knows how to read

- **Date**: 2026-09-17
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `ResolveAnthropicCredential`, `credentials.json`, `claudeOAuth`, `anthropic credential`, `oauth`, `daneel-dreams`, `M-DANEEL-DREAMS` across `design_docs/` — none found. The closest material is the OAuth-vs-API-key mis-billing incident recorded in `design_docs/v1-mission.md` (~line 310, "OAuth Fable was available the whole time" / nested `claude -p` billed via `ANTHROPIC_API_KEY`) and echoed in the precedence warning atop `internal/ai/anthropic_auth.go` (`ResolveAnthropicCredential`). That incident is context, not a ruling on this path.

Forwarded from Daneel (user inbox `inbox_1789634045256_38657aa9`, verified against HEAD `1f78cd2bc`). All three claims reproduce in code:

1. **OAuth lane unreachable via the CLI.** `cmd/ailang/ai_handlers.go` (`buildAIHandler`) always passes `factory.WithAPIKeyEnv(model.EnvVar)`, and `internal/ai/factory/factory.go` (`New`, the `ProviderAnthropic` case) returns `"<ENV> environment variable required"` the moment `apiKeyEnv` is set but empty — *before* `ai.ResolveAnthropicCredential()` is ever called, so the `~/.claude/.credentials.json` lane is dead on the `ailang run --ai` path. A machine with a valid Max subscription credential is refused at startup and (per the reporter) falls through to another provider.
2. **No refresh.** `claudeOAuth` in `internal/ai/anthropic_auth.go` declares only `AccessToken`/`ExpiresAt`; `RefreshToken` is never parsed, and `valid()` can only tell the user to "run any `claude` command to refresh it". On macOS the credential also lives in the login keychain (read only by `internal/mission/anthropic_quota.go`), not by this in-process path.
3. **Cross-provider `AI.step` is blocked by design.** The `ModelResolver` contract in `internal/effects/ai.go` explicitly returns `ModelNotAllowed` when a per-call model resolves to a different provider than the bound handler. Confirmed as documented behaviour, not a bug — but it means the DREAMS use case cannot route around claim 1 at the AILANG level.

**Why design-doc, not direct-fix.** The driver is Daneel's nightly dream (`M-DANEEL-DREAMS`, daneel#69): `--ai` must ride the Max subscription, not a metered key. The obvious mechanical change (fall through to `ResolveAnthropicCredential` when `apiKeyEnv` is set but unset) is small, but it is a *billing-lane precedence* decision on the exact axis where this fleet already logged one real mis-billing incident (an inherited key silently outbidding keychain OAuth). Where the file lane sits relative to a configured-but-unset env var is a ruling someone could disagree with, not a two-line edit. The refresh half (claim 2) adds real semantics: an HTTP token-refresh flow and/or a credential rewrite, which is security-sensitive, and macOS keychain access is a second lane with its own capability question. Spans at minimum `factory.go`, `anthropic_auth.go`, `ai_handlers.go` (+ a decision on macOS keychain), with at least three defensible designs (silent fall-through vs. explicit `--ai-oauth` opt-in vs. precedence reorder; in-process refresh vs. instruct-user refresh). Claim 3 needs a separate, deliberate ruling if cross-provider per-call routing is ever wanted — recommend scoping it out of the OAuth fix and into its own doc only if DREAMS actually needs it.

**Repro (claim 1)**: `env -u ANTHROPIC_API_KEY ailang run --caps IO,AI -ai claude-opus-5 --entry main -args-json '{"model":"claude-opus-5"}' probe.ail` with a valid `~/.claude/.credentials.json` → refused with "ANTHROPIC_API_KEY environment variable required".
