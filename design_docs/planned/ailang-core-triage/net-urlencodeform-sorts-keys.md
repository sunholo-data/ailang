# std/net.urlEncodeForm sorts keys alphabetically (Go url.Values.Encode)

- **Date**: 2026-09-28
- **Class**: already-covered
- **Recommend**: duplicate-of design_docs/implemented/v0_19_2/m-stdlib-url-encode.md
- **Searched**: `urlEncodeForm`, `parseQuery`, `url.Values.Encode` across design_docs/, docs/, std/, internal/builtins/; behavior reproduced live (`ailang run`: `urlEncodeForm([{name:"skippages",value:"2"},{name:"pagesize",value:"20"}])` → `pagesize=20&skippages=2`)
- **Estimate**: omit (no fix recommended)

The report's premise — that the reordering is undocumented and surprising — is wrong at the authoritative documentation layer. The sorting is already documented, with the exact order-sensitive escape hatch the report asks about, in two places: (1) the `urlEncodeForm` doc comment in [std/net.ail](std/net.ail) ("Keys are sorted alphabetically (Go url.Values.Encode behavior); if you need order-preserving output for signing schemes (AWS SigV4, OAuth1.0a), build the body manually with urlEncode on each value"), and (2) the identical `LongDesc` on the `_net_url_encode_form` builtin in `internal/builtins/net.go` (`registerNetURLEncodeForm`), which is what `ailang doctor` and the agent-facing stdlib discovery surfaces render. The design doc that shipped the function, `design_docs/implemented/v0_19_2/m-stdlib-url-encode.md`, pinned the Go backing (`url.Values.Encode()`) as the chosen implementation, and its successor `design_docs/implemented/v0_30_0/m-stdlib-url-parse.md` deliberately built `parseQuery` to *not* share that behavior (splitting the raw string to preserve order and duplicates) — so the encode-sorts / parse-preserves asymmetry is a known, intentional design split, not an oversight. The only surface where the caveat does not appear is the website `docs/docs/reference/stdlib.md`, which is a module-level index (one line per module, no per-function contracts) and is not the canonical home for builtin semantics; per-function contracts live in the doc comments and builtin metadata, which both cover this. Should anyone want order-preserving form encoding as first-class behavior (making `urlEncodeForm` a true inverse of `parseQuery`), that is a public-surface semantics change and would need its own design doc — but nothing in this report establishes a defect.
