# Ollama per-call deadline ignores the model's declared generation_timeout; standard-mode lane banks the resulting 300s kill as api_error

- **Date**: 2026-11-05
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `OLLAMA_HTTP_TIMEOUT`, `ollamaCallContext`, `defaultOllamaV1Timeout` in `design_docs/`; `generation_timeout` in `design_docs/ internal/`; `CategorizeStandardAPIError`, `ErrorCategoryTimeout` in `design_docs/`; prior triage row `ai-deadline-and-named-test-roundtrip.md`; implemented `v0_33_1/m-ollama-v1-streaming-idle-timeout.md`; planned `m-ai-call-context.md` and `planned/v0_29_0/m-eval-stream-health-retry.md`
- **Estimate**: omitted (design-doc)

**Both halves verified in code.** (1) `internal/ai/ollama/step.go` (`defaultOllamaV1TimeoutSec`, `ollamaV1Timeout`, `ollamaCallContext`) applies a flat 300s context deadline to every call whenever `AILANG_OLLAMA_HTTP_TIMEOUT_SEC` is unset, and `internal/ai/ollama/client.go` (`Client.Generate`, the comment says "No-op when called via Step" but the no-op is only against double-wrapping, not the 300s itself) applies it to the standard-mode single-shot path too. Nothing reconciles this with the per-model `generation_timeout` (`internal/modelreg/models.go` `GenerationTimeoutSeconds`, yaml key `generation_timeout`) — the two budgets live in disjoint layers and the provider never sees the model registry. (2) The standard-mode lane classifies through `internal/eval_harness/error_categorizer.go` (`CategorizeStandardAPIError`, called from `cmd/ailang/eval_benchmark.go` at the generation-failure branch), which has NO timeout bucket — every non-refusal, non-stall error falls to the `api_error` catch-all — while the agent-path categorizer in the same file already maps "context deadline exceeded" to `ErrorCategoryTimeout` ("a slow-but-capable model just needed more time"). So the report's two asks split along exactly the seam this repo has already drawn elsewhere.

**This is a re-occurrence of a measured pattern, already solved for a different lane — not a duplicate.** `design_docs/implemented/v0_33_1/m-ollama-v1-streaming-idle-timeout.md` measured the identical mechanism on the streaming agent path (182/2058 sessions killed at the 300s cap; the doc's own verification table pins `defaultOllamaV1TimeoutSec = 300` at `step.go` — same const, still :25 today) and fixed it with a TTFT/idle/total split plus a **stopgap** `AILANG_OLLAMA_HTTP_TIMEOUT_SEC=1800` pinned in two launchd plists. The standard-mode lane evidently does not inherit that stopgap env (7/66 standard-lane runs died at ~300s on 2026-11-05), so the fix shipped for one call site left the other exposed. The report's remedy — derive the per-call deadline from the model's `generation_timeout` — is nonetheless not a mechanical patch, for two reasons that make it design-doc territory: (a) `GenerationTimeoutSeconds` is documented in `modelreg` as a **per-token idle budget after first event**, not a total wall-clock cap, and lanes disagree on which it is (`planned/v0_29_0/m-eval-stream-health-retry.md` explicitly splits TTFT / inter-token idle / total as three distinct budgets, and warns against false-killing slow-but-healthy generations); deriving a *total* HTTP-call deadline from an *idle* budget, or taking the max, are both defensible and not equivalent — this is row 3, a decision someone could disagree with. It also crosses the provider/registry layer boundary (`internal/ai` currently knows nothing of `internal/modelreg`; plumb it via `ai.Request` or a new config source — again a choice). (b) The second half (a distinct timeout category in standard mode) is small in isolation but is a change to banked-data classification semantics (`error_category` feeds the regression detector's `INFRA_CATEGORIES` per `m-eval-stream-health-retry.md` Goal 4), and belongs in the same design pass so the standard lane's categories converge with the agent lane's rather than growing a third vocabulary. Per CLAUDE.md principle 2, the design doc must also keep the fail-loud property: an env override and a derived deadline must never silently mask a wedge — the "max, not override" framing in the report is the right starting posture.

**Cross-references for the designer:** start from `m-ollama-v1-streaming-idle-timeout.md` (the same 300s-vs-turn-length measurement, the stopgap to retire or extend to the standard lane's launch context, and the idle-timeout machinery in `internal/ai/ollama/idlereader.go`); `planned/m-ai-call-context.md` (v0.55) owns deadline *plumbing* for the AI effect generally — coordinate so the eval-harness lane's model-derived deadline and the effect-level deadline don't fight over the same context; `planned/v0_29_0/m-eval-stream-health-retry.md` owns the TTFT/idle/total semantics and the distinct-infra-category labelling contract this report's second half should reuse, not reinvent. The triage row `ai-deadline-and-named-test-roundtrip.md` covers a different gap (std/ai builtins with NO deadline at all) — adjacent, not covering.
