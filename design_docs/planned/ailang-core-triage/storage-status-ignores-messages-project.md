# `ailang storage status` ignores AILANG_MESSAGES_PROJECT and names the wrong project for the messaging store

- **Date**: 2026-09-29
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `AILANG_MESSAGES_PROJECT` (design_docs/), `storage status` (design_docs/), ailang-core-triage backlog (40 files, none mention it)
- **Estimate**: ~15–25 lines in `cmd/ailang/storage.go` **plus** a new regression case in `cmd/ailang/storage_test.go` (2 files, well over `DIRECT_FIX_MAX_LINES`=2)

The report is verified against the code. `resolveMessagesTarget` (`cmd/ailang/messages.go:177`) resolves the messaging project as `AILANG_MESSAGES_PROJECT` first, then `config.CloudProject` — so `ailang messages list` correctly uses `ailang-multivac` when `AILANG_MESSAGES_PROJECT=ailang-multivac` is set (the mission-stage pin, `MissionMessagePlaneProject` in `internal/config/mission.go`). But `writeStorageStatus` (`cmd/ailang/storage.go:60`) resolves **one** project for all gcp rows via `config.CloudProjectSource`, which only knows `AILANG_CLOUD_PROJECT > GOOGLE_CLOUD_PROJECT > config.yaml > metadata` — `AILANG_MESSAGES_PROJECT` is not in its chain. So the one command whose job is to confirm where messages actually go prints the cloud-plane project (`ailang-multivac-dev` / `multivac-internal-dev`) on the messaging row while the messages commands read `ailang-multivac`. This is exactly the failure class M-V1-SIMPLIFY-S3 M3 built per-store status to prevent ("the status could say 'local' while `ailang messages list` read Firestore") — the mode half is right, the project half is not. The S3 sprint plan (`design_docs/planned/m-v1-simplification-s3-sprint-plan.md`, M3) specifies the per-store output but never rules on the messaging-project precedence, so this is a spec gap, not a doc violation.

Why design-doc and not direct-fix: the fix is not one line. The correct change is for the messaging row's project to come from the same resolution `resolveMessagesTarget` uses (ideally a shared helper in `internal/config` so the two can't drift again — `config.MessagesProject()` first, labelled with its source, falling back to `CloudProjectSource`), keeping the coordinator/observatory rows and the hybrid shared-plane line on the cloud-plane resolver. That is a semantics decision about which resolver owns which row, plus a shared-helper refactor across `internal/config` and `cmd/ailang`, plus a regression test that sets `AILANG_MESSAGES_PROJECT` and asserts the status output names its project and source. More than 2 lines, more than 1 file — rows 5 and 6.
