# verify: proofs reason over Z3 unbounded Int but the runtime int is wrapping int64 — VERIFIED then garbage at runtime

- **Date**: 2026-09-28
- **Class**: bug (soundness gap in what VERIFIED means) + feature (--int64 flag / lint) + docs
- **Recommend**: design-doc
- **Searched**: `z3`, `SMT`, `BitVec`, `overflow`, `int64`, `wraps`, `unbounded`, `mathematical integer` across `design_docs/`, `docs/`, `internal/smt/`; `solver-friendly`, `string solver`, `contains` across `design_docs/` and `docs/docs/`; existing triage rows `verify-ensures-verified-without-encodable-refutation.md`, `smt-encode-dt-builtins.md`, `v047-numerics-followups-*.md`; planned docs `m-contract-verification-coverage.md`, `m-verify-bounded-unrolling-false-counterexample.md`
- **Estimate**: n/a (design-doc)

The report is sound and the mechanism is confirmed in code: the SMT encoder maps AILANG `int` to Z3's unbounded `Int` sort (`internal/smt/types.go`, `sortForType` returning `"Int"`) with `mul_Int` encoded as `*` (`internal/smt/codegen_operators.go`), so every `ensures` proof — including correct ones with proper rounding contracts — holds over mathematical integers; meanwhile the evaluator carries Go `int64` (`internal/eval/eval_expressions.go`) which wraps silently. So `toBase(amount, rate) = roundDiv(amount*rate)` verifies over ℤ and produces garbage at 10^15 × 10^8. Nothing in the repo acknowledges the width mismatch: `grep -r BitVec` over `internal/smt/` and `design_docs/` returns nothing, and no doc states "proofs are over unbounded integers; bound products with `requires`". The string-solver half is the same shape: strings encode to Z3 Seq/String theory (`String` sort, `str.*` predicates, `internal/smt/types.go`), where `find(result,"$") == length(a)` on a concatenation is a known-hard formulation vs. `str.prefixof`/`str.contains`, and there is no doc guiding solver-friendly predicates.

Why design-doc, not direct-fix: the reporter offers three remedies with materially different semantics and cost, and they are not combinable-by-default — (a) a docs/prompt/verify-output note is honest but pushes the burden onto every verified program's author; (b) `--int64` encoding as `(_ BitVec 64)` changes what VERIFIED means (some currently-verified goals — e.g. anything relying on ℤ associativity or division reasoning — may become unprovable or need SMT-integer-to-bitvec bridges), while the range-obligation alternative keeps the Int encoding but adds `requires`-style bounds obligations for every arithmetic result, changing the gate's contract (row 4) and risking false counterexamples on currently-clean code; (c) the overflow lint adds a new warning surface to the verify output that models and the eval harness consume. Any of these touches the verifier's trust contract — precisely what the existing verifier docs treat as design territory (`m-verify-bounded-unrolling-false-counterexample.md` rules a `sat` is not a violation; `m-contract-verification-coverage.md` splits the skip taxonomy; the backlog row from 2026-09-15 covers proof/refutation asymmetry) — and none of them rules on this width mismatch (`none found` for: BitVec, overflow, unbounded, int64 across design_docs/ and internal/smt/). A single design doc should decide (a) vs (b-variant) vs (c), whether they ship together or staged, and fold in the string-predicate guidance note as a docs milestone of the same doc since both are "tell the user which obligations the solver/semantics can actually carry".
