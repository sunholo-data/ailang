# --bytecode silently drops Rand[mode=crypto|seeded] (no D-C fail-closed stub for Rand modes; VM rand not mode-aware)

- **Date**: 2026-10-02
- **Class**: bug (security)
- **Recommend**: design-doc
- **Searched**: `pushRandModeIfDeclared`, `Rand[mode`, `declaresNetScope`, `Net[scope=public]`, `Phase 2E`, `EvalOnly`, `m-net-scope-public`, `m-bytecode-phase2e-sprint-plan`
- **Estimate**: n/a (design-doc) — the minimal stub extension alone is ~20–30 lines in `internal/gen/lower/program.go`, but the report's full ask (native VM path honouring Rand modes after Phase 2E, plus the related #1449 double-execution fix) spans 4+ packages and forces open design decisions.

**Why**: Verified statically at commit c22d2d5a1 (no Go toolchain in this environment, so the repro was not executed — every claim below was confirmed by code reading; the repro script in the report should still be run by the fix session as its first step).

The mechanism is exactly as reported. The evaluator pushes the declared Rand mode at nested lambda entry (`internal/eval/eval_apply.go:135`, `applyFunctionValue` → `pushRandModeIfDeclared` in `eval_evaluator.go`; mode stack and `SeededModeError` in `internal/effects/rand_mode.go`). Under `--bytecode`, `internal/gen/lower/program.go` (`lowerFuncDecl`, ~line 306) lowers `Net[scope=public]` functions to evaluator-only stubs per M-NET-SCOPE-PUBLIC D-C — `declaresNetScope` — but has **no equivalent for Rand modes**: a `Rand[mode=seeded|crypto]` function lowers to real bytecode, runs on the VM (which has no moded-frame hook, V9 of the same doc), and any call bridged back to the evaluator (`internal/runner/bridge.go`, `CallEvalFunc` → `CallValueN`) executes with the VM-side caller's mode never pushed, so `CurrentRandMode()` is `os` and the draw comes from math/rand. No error is raised; the strict-bytecode path fails loudly only because `__rand_int` is an unwired effectful builtin ("Phase 2E" message in `internal/runner/vm.go:216`), not because the mode was dropped.

This is **not a duplicate** of an existing doc, but the ratified precedent is directly adjacent: `design_docs/implemented/v0_52_0/m-net-scope-public.md` decision D-C ("Bytecode VM fails closed") states the exact rule — "Silently dropping a security mode on one execution path is a silent fallback" — and applies it to Net only. Rand was simply not in scope there. A fix session should reuse the D-C shape (short-term: extend the lowering stub to functions declaring a non-os Rand mode, mirroring `declaresNetScope` → e.g. `declaresRandMode`, which alone makes the repro error `RAND_SEEDED_NO_SEED` under `--bytecode`) and then decide the Phase 2E end-state.

The design decisions the doc must pin (rubric rows 3/4/5 — more than one acceptable remedy, changes the security/execution-semantics contract, spans `internal/gen/lower` + `internal/eval` + `internal/bytecode/compiler` + `internal/vm` + `internal/runner` + tests):

1. **Short-term fail-closed**: which modes trigger the evaluator-only stub (crypto + seeded; plain `Rand`/os stays on the VM), and whether the stub reason text distinguishes Rand from Net.
2. **Phase 2E native path**: whether the VM gets a moded-frame hook (push/pop on call/return, mirroring `replaceable`'s non-replaceable-frame rule) with mode-aware rand dispatch behind the `vm.EvalInterop` seam, or whether non-os Rand functions stay evaluator-only permanently (the cheaper, D-C-consistent option — argue it explicitly).
3. **Seeded source across the boundary**: the seeded PRNG lives on the EffContext (`randModeState`); if the VM ever draws directly it needs access to the same per-context source or determinism guarantees break.
4. **Related #1449 double-execution** (confirmed at `internal/runner/entrypoint.go:143-158`: non-strict `--bytecode` falls through to the evaluator after any VM runtime error, re-running side effects): decide whether to fix in the same doc (e.g. abort instead of fall back after dispatch started) or park as a follow-up — it is a correctness issue on the same code path but separable.
5. **Regression tests** per the report: the repro under `--bytecode` must error `RAND_SEEDED_NO_SEED`; a crypto-mode probe must draw via crypto/rand on both fallback and (post-2E) native VM paths. Parity harness (`internal/testing/engine_parity_test.go`) and strict-bytecode gate coverage belong in the sprint plan.

Related, non-conflicting context: `design_docs/planned/v1_0_0/m-effect-refinement.md` (Rand as the pilot effect for replay contracts) and the archive `design_docs/archive/rand-determinism-sitrep.md` for the seeded-source rationale. The consumer risk cited in the report is real: crypto-mode draws feed api_keys.ail (docparse) and the sunholo/mcp_oauth flow (see `design_docs/planned/v0_52_0/m-mcp-oauth-package.md`, ratified — its S0 sibling #1522 is the Net half of the same fail-closed rule).
