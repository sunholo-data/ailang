# serve-api silently coexists with coordinator on 127.0.0.1:8765; requests split between listeners

- **Date**: 2026-09-15
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `serve-api`, `SO_REUSEPORT`, `port collision`, `8765`, `already in use`, `loopback redirect` across design_docs/ — no existing doc covers serve-api/coordinator port overlap (m-serve-api-* docs cover routes/filtering, not binding)
- **Estimate**: ~15–25 lines in `internal/apiserver/server.go` + one line in the sunholo/oauth AGENT.md example

**Why (mechanism, verified in code):** not SO_REUSEPORT — Go's `net.Listen` never sets it here. The real cause is a specific-vs-wildcard bind pair: the coordinator daemon health server binds `127.0.0.1:PORT` (`internal/coordinator/daemon_http.go:90`, `host := "127.0.0.1"`, started when `PORT` is set — the M1 plist/installer default is 8765 per `cmd/ailang/messages_send.go:50`), while serve-api binds the wildcard `:PORT` (`internal/apiserver/server.go:494`, `httpAddr := fmt.Sprintf(":%s", s.port)`, served by `srv.ListenAndServe()` at `:531`). BSD/macOS allows binding the wildcard address when a specific loopback bind already exists, so both succeed, `ListenAndServe` never surfaces EADDRINUSE, and the kernel delivers loopback connections to either listener (typically the more-specific one, appearing "random" in practice). serve-api's startup banner prints unconditionally (`printStartupBanner()` before `ListenAndServe`), so the operator sees a normal launch. Note `cmd/ailang/server.go:299` already has an `isPortInUse` probe used by the UI server — serve-api lacks the equivalent. Also, because the coordinator binds a different address family shape, a naive "bind first, check error" fix must probe the exact host it will serve (or bind explicitly with `net.Listen` and keep the listener) rather than trust `ListenAndServe`'s late error.

**Decision points worth a doc (row 3, multiple acceptable remedies):** (a) refuse at startup with a probe vs. bind-and-fail-fast vs. warn-and-continue; (b) whether to identify the holder (pid/port owner via lsof/ss) in the error, which is platform-specific; (c) whether the coordinator should keep binding loopback-only while its health endpoint doubles as a user-facing 404 source on shared ports; (d) the oauth AGENT.md loopback-redirect example port (8765 → e.g. 8766) is a doc change but touches an external repo's quick start, which should be an explicit decision, not a drive-by. Combined scope spans apiserver + coordinator docs + an external AGENT.md, past the direct-fix thresholds.
