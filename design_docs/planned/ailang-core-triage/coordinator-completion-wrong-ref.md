The reporter measured the mechanism precisely, so the fix is bounded: something between coordinator v0.38.2 and v0.38.4 (the pre-flight added before the clone + PR step) changed which ref the executor pushes — the agent commits to its own `design-doc/<slug>` branch (as the design-doc-creator skill instructs) and pushes it, but the coordinator then creates an empty `coordinator/task-*` at the base commit and reports `branch_name: coordinator/task-*` with the changed file named on it (verified 404 on the reported branch, file present on the agent's branch; no PullRequestEvent; contrast task-389b7a51 on 12 Sept where the commit was ON the coordinator branch and PR #2 opened). The fix is to push the ref the agent's HEAD is actually on, or check the agent's branch out of the task branch before the PR step — mechanical once the v0.38.2→v0.38.4 diff is read, not a design decision; Mark has already ruled on the related policy question ("We don't have PRs for design docs, that's fine — but work needs to land in the repo"), so the auto_merge docs-only landing is instruction, not a trade-off. Daneel now verifies each reported file on the reported branch before mailing links, so until this lands every design-doc report will read "Reported but NOT on branch".

Relation to existing docs: `m-coordinator-execution-trust.md` (V24) warns that branch/PR handling is containment-sensitive — the fix should keep tiering/containment semantics intact (pushing the agent's HEAD ref must not open the `AILANG_PUSH_BRANCH` direct-push path to untrusted tasks), but that is a constraint on the fix, not a reason for a design doc.
