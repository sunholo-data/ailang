# `std/json.getInt` silently truncates non-integral JSON numbers

- **Date**: 2026-09-28
- **Class**: bug
- **Recommend**: design-doc
- **Searched**: `getInt`, `truncat` across `design_docs/`; the implementing doc `design_docs/implemented/v0_7_0/m-json-helpers.md` ("Get integer field (truncates)" — truncation was intentional at design time, not an accident); sibling triage row `ailang-core-triage/stdlib-number-naming-and-result-option-convention.md` (same accessor family, naming/Option-vs-Result focus, does not rule on truncation semantics); `grep -rn "getInt" docs/ prompts/` (the v0.11.4 prompt *teaches* "JSON numbers are floats, getInt truncates"); `ailang docs std/json` ("(truncates float)"). No planned doc rules on lossiness of int getters.
- **Estimate**: omitted (design-doc)

**Verified by reproduction** on v0.47.0: `decode("{\"b\":1187.50}")` then `getInt(j, "b")` returns `Some(1187)`, while integral values (`0.00`, `5820`) round-trip fine. The mechanism is `std/json.ail` (`getInt`): `Some(f) => Some(floatToInt(f))` — a straight truncation with no integrality check, exactly as designed in the v0_7_0 doc. So this is not a code bug against the current spec; it is a report that the current spec is wrong, and the reporter's field evidence (sunholo/economic against e-conomic REST amounts like `1187.50`) shows the failure mode: a money API sending decimals plus a caller picking `getInt` drops minor units silently, and `Option`'s `Some` makes the loss look like success.

Why design-doc and not direct-fix: the reporter themselves offers two different remedies (strict `getInt` returning `None` on non-integral, plus a separately-named `getIntTrunc`; or document-only), and a third exists (keep truncation, rename, deprecate). More than one acceptable answer is rubric row 3. Separately, changing `getInt`'s return contract on a non-integral input is a public stdlib-surface semantics change (row 4) under the stability promise (`design_docs/implemented/v0_29_0/m-v1-stability-promise.md`: deprecations live ≥1 minor), and it is not one file's problem: the truncation contract is written into `std/json.ail`, the `ailang docs` LongDesc, `docs/docs/reference/option-vs-result.md`, and the prompt's worked example — all four would need to move together, and the golden/inline test `getInt converts float to int` in the v0_7_0 doc would need a deliberate semantics decision, not a drive-by edit.

Scope guidance for the eventual doc (not a decision here): decide (a) strict-vs-truncating default and the truncating sibling's name; (b) whether the guard lives in the stdlib wrapper (`intToFloat(floatToInt(f)) == f` — `std/math` is already imported by `std/json.ail`, so no builtin work is needed) or as a JSON-level distinction between `1187` and `1187.50` at decode time (a deeper change the doc should explicitly reject or scope); (c) migration path for existing callers under the stability promise; (d) whether `decodeFloatArray`/array-valued getters inherit the same ruling. This row and `stdlib-number-naming-and-result-option-convention.md` should be resolved by one design doc covering the `std/json` number-accessor family — same file, adjacent complaints, one coherent contract — but they are separate reports and neither duplicates the other.

Related but not duplicates: `v047-numerics-followups-show-ingest-docs-macos.md` item 1 is about `show()` truncation (a different silent-truncation class, different surface); `m-investigate-xpkg-int-float-coercion.md` is archive-era and about the xpkg int/float coercion chain, not the JSON getters.
