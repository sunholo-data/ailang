## Problem Statement

ADT types require manual equality functions, creating 10-15 lines of boilerplate per enum type.

**Current State:**
```ailang
type DeckID = Bridge | ObservationDeck | Engineering | Medical | Cargo | Crew | Recreation

-- Manual equality function: 15+ lines of boilerplate
pure func deckIDEquals(a: DeckID, b: DeckID) -> bool =
    match a {
        Bridge => match b { Bridge => true, _ => false }
        ObservationDeck => match b { ObservationDeck => true, _ => false }
        Engineering => match b { Engineering => true, _ => false }
        Medical => match b { Medical => true, _ => false }
        Cargo => match b { Cargo => true, _ => false }
        Crew => match b { Crew => true, _ => false }
        Recreation => match b { Recreation => true, _ => false }
    }
```

**Impact:**
- ~10-15 lines per enum type
- Error-prone: easy to miss a case or typo
- Obscures real business logic with mechanical code
- stapledons_voyage has 13 ADT types, potentially 130-195 lines of boilerplate

## Goals

**Primary Goal:** Automatically generate equality functions for ADT types.

**Success Metrics:**
- `deriving (Eq)` syntax supported on type declarations
- Generated equality function has correct semantics
- Works with nullary constructors (enum-like ADTs)
- Works with constructors with fields
- Reduces boilerplate by 10-15 lines per type

## Solution Design

### Overview

Add `deriving` clause to type declarations that automatically generates equality functions.

### Syntax Options

**Option A: Haskell-style deriving clause**
```ailang
type DeckID deriving (Eq) = Bridge | ObservationDeck | Engineering | Medical | Cargo | Crew | Recreation
```

**Option B: Post-definition deriving**
```ailang
type DeckID = Bridge | ObservationDeck | Engineering | Medical | Cargo | Crew | Recreation
    deriving (Eq)
```

**Option C: Derive annotation**
```ailang
@derive(Eq)
type DeckID = Bridge | ObservationDeck | Engineering | Medical | Cargo | Crew | Recreation
```

**Recommendation:** Option A (Haskell-style) is most familiar to functional programmers.

### Generated Code

For a type like:
```ailang
type DeckID deriving (Eq) = Bridge | ObservationDeck | Engineering
```

Generate:
```ailang
-- Auto-generated by deriving (Eq)
pure func eqDeckID(a: DeckID, b: DeckID) -> bool =
    match a {
        Bridge => match b { Bridge => true, _ => false }
        ObservationDeck => match b { ObservationDeck => true, _ => false }
        Engineering => match b { Engineering => true, _ => false }
    }
```

For ADTs with fields:
```ailang
type Tree deriving (Eq) = Leaf(int) | Node(Tree, int, Tree)
```

Generate:
```ailang
pure func eqTree(a: Tree, b: Tree) -> bool =
    match a {
        Leaf(x) => match b { Leaf(y) => x == y, _ => false }
        Node(l1, v1, r1) => match b {
            Node(l2, v2, r2) => eqTree(l1, l2) && v1 == v2 && eqTree(r1, r2)
            _ => false
        }
    }
```

**Phase 1: Parser Support** (~2 hours)

### Example 2: ADT with Fields

**AILANG:**
```ailang
type Option[T] deriving (Eq) = None | Some(T)
```

**Generated:**
```ailang
pure func eqOption(a: Option[T], b: Option[T]) -> bool =
    match a {
        None => match b { None => true, _ => false }
        Some(x) => match b { Some(y) => x == y, _ => false }
    }
```

## Non-Goals

**Not in this feature:**
- Other derivable type classes (Show, Ord, etc.) - can be added later
- User-defined deriving mechanisms
- Instance constraints (e.g., `Eq a => Eq [a]`)

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Parser ambiguity with `deriving` | Medium | Use clear syntax, test edge cases |
| Recursive types causing infinite loops | Low | Same as manual equality functions |
| Generic types require constraints | Medium | Start with monomorphic types only |
