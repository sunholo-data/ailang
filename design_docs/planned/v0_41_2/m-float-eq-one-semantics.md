# M-FLOAT-EQ-ONE-SEMANTICS — one answer to `NaN == NaN`, on every path

**Status**: Planned. **Blocked on design freeze (D1).**
**Target**: v0.41.2
**Priority**: P1. It is a correctness bug: the same comparison answers differently depending on
how the compiler lowered it
**Estimated**: ~3h once D1 is decided
**Dependencies**: None. Follows M-EQ-DERIVE-CONTAINERS (`6d096fe98`), which pinned one of the
divergences in `cmd/ailang/eq_parity_test.go`
**Tracking**: [#1274](https://github.com/sunholo-data/ailang/issues/1274)

## Problem Statement

AILANG has **five** implementations of float equality, and they disagree on NaN. Which one runs
is decided by lowering, not by the program. Verified live 2026-09-22 (dev + `6d096fe98`,
`AILANG_NO_CACHE=1`), `export func main() -> bool = <expr>`:

| Expression | evaluator | `--bytecode` VM |
|---|---|---|
| `(0.0 / 0.0) == (0.0 / 0.0)` | **true** | **false** |
| `(0.0 / 0.0) != (0.0 / 0.0)` | false | true |
| `eqp(0.0 / 0.0, 0.0 / 0.0)` with `func eqp[a](x: a, y: a) -> bool { x == y }` | **false** | false |
| `(\p. \q. p == q)(0.0 / 0.0)(0.0 / 0.0)` | true | false |
| `[0.0 / 0.0] == [0.0 / 0.0]` | true | true |

The evaluator disagrees **with itself**. `nan == nan` is true, but the same comparison through a
generic function is false. The VM disagrees with the evaluator on the top-level case.

**Impact.**
- **Determinism (A1).** A refactor that moves `==` into a helper changes the program's output.
- **Detectability.** std has no `isNaN` (V6). The universal idiom `x != x` is the only NaN test
  available, and on the dictionary path it returns **false** for NaN, so NaN cannot be detected
  there at all.
- **Evals.** Benchmark expected outputs are generated by Python/JS/Go reference programs, all IEEE.
  How often this bites is unmeasured; it is likely rare, since it needs NaN reaching an `==`.

## Goals

**Primary goal:** one NaN rule for `==`/`!=` on floats, identical on every lowering path and both
backends, bare or nested in a container.

**Success metrics:**
- Every row of the problem table gives the same answer in the evaluator and the VM, and the
  top-level and nested rows are consistent with each other under the chosen rule
- A NaN predicate exists that works regardless of the rule
- `cmd/ailang/eq_parity_test.go` has no "documented divergence" rows left

## High-Impact Decisions

| Decision | Why High Impact | Chosen By | Deadline | Change Cost |
|----------|-----------------|-----------|----------|-------------|
| **D1: IEEE or lawful?** | Observable semantics of every float comparison | **human** | before sprint | med (flip later = same work again) |
| D2: Add `std/math.isNaN` | Only way to test for NaN under a lawful rule; convenience under IEEE | agent | sprint | low |
| D3: Keep `Value.Equal`'s NaN==NaN for constant-pool dedup, but stop OpEq reaching it for nested floats | Dedup is a legitimate separate use | agent | sprint | low |

**D1 options:**

- **(A) IEEE everywhere (recommended).** `NaN == NaN` is false and `NaN != NaN` is true, bare or
  nested. This matches Python, JS, Go, Rust (`PartialEq`) and Haskell (`Eq Double`), and so every
  benchmark reference program and every model's prior. Two of the four runtime paths (V2, V3 top
  level) and the shim (V5) are already IEEE. The cost: `Eq[Float]` stops being a lawful equivalence
  relation (reflexivity fails for NaN), exactly as in Haskell and Rust, and `[nan] == [nan]`
  becomes false. That reverts the lawful choice `6d096fe98` made for structural comparison.
- **(B) Lawful everywhere.** `NaN == NaN` is true on every path. Reflexivity holds, and
  dedup/membership (`contains(xs, nan)`) behave. The cost: it diverges from every reference
  language, `x != x` stops detecting NaN, so `isNaN` (D2) becomes mandatory, and the VM's OpEq and
  the `eq_Float` builtin both flip.

## Solution Design

### Overview

Make one float-equality function authoritative and route all five paths through it:
1. `types/dictionaries.go` `registerEqFloat` (eq and neq)
2. `eval/builtins_comparison.go` `eq_Float`/`ne_Float` and the `builtins/math_comparison.go` registry twin
3. `vm/vm.go` `runtimeEq`: for **nested** floats, recurse with the same rule instead of falling
   through to `Value.Equal` (D3 keeps `Value.Equal` for dedup)
4. `eval/eval_equality.go` `valuesStructurallyEqual` float case
5. `eval/eval_operations.go` `applyBinOp` float branch

A shared `floatEq(a, b float64) bool` cannot live in one place: `vm` and `eval` must not import
each other, and `types` holds the dictionary. Put it in the lowest common package (`internal/types`
already imports `math`, and `eval`/`vm` both import `types`). Confirm the import graph in Phase 0
with `make check-boundaries`.

### Implementation Plan

**Phase 0 (~0.5h):** a parity test with every table row plus a `!=` column and a Go-codegen column
(V8). Record current output.
**Phase 1 (~1.5h):** `types.FloatEq`, used by the five paths. `std/math.isNaN` (D2).
**Phase 2 (~1h):** update `TestEqual_Float_NaN` and `eq_parity_test.go` deliberately. Add a
teaching-prompt line stating the rule, verified with `ailang check`. CHANGELOG.

## Conflict Surface

Touches `internal/types`, `internal/eval` and `internal/vm`.
1. **Positions extended:** none syntactically; semantically the float case of `==`/`!=` on every path.
2. **Coexisting constructs:** constant-pool dedup (`Value.Equal`, must keep NaN==NaN: D3). `Ord`
   on floats (`<` with NaN is false on both backends today and stays that way). `show(nan)`.
3. **Disambiguation:** n/a (no parse change).
4. **Must still work:** `examples/eq_containers.ail` (26 checks, no NaN), `examples/deriving_eq.ail`,
   `internal/bytecode` dedup tests, `TestEqEvaluatorVMParity` non-NaN rows.
5. **Deliberately changes:** under (A), `nan == nan` on the dictionary path flips to false and
   `[nan] == [nan]` flips to false. Under (B), `eqp(nan, nan)` and VM top-level flip to true.
