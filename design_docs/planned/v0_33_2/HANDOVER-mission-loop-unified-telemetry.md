## What each milestone actually did

**M2 — the money adds up now.** Two defects with different owners: `PostIteration` never called
`UpdateStageStatus` (writer), and the poster supplied zero tokens (caller). `IterationStage` gained
`Status` from the existing vocabulary; the mission-control skill now posts tokens and real per-stage
outcomes; stage cost/tokens aggregate into the chain total. Measured before/after on the iter-190
shape through the built binary: 4 stages all `pending`, $0.0000, 0 tokens → completed/failed,
$0.1077, 37,414 tokens.

**M3 — the remote copy is joinable, not an island.** `chains post-iteration` writes to the local
store and, when a node names one, a remote one. The part that is easy to miss: both stores must hold
the SAME chain and stage ids, or a span carrying the local id can never join the remote copy. So
`ChainCreateRequest`/`StageCreateRequest` take an optional `ID`, `PostIteration` backfills the post
with what it wrote, and a pinned id is never regenerated by `CreateStage`'s UNIQUE retry. Backend
selection reuses `storage.NewBackendsForMode` (the same switch `NewBackends` uses, with the mode as a
parameter). Each target keeps its OWN bounded spool — sharing one would let a cloud outage evict
local posts that were only waiting on a locked database.

## Open follow-ups, in priority order

**1. M1's linkage does not yet reach the MISSION loop** (found while doing M3; not a regression).
The only production site that sets OpenRouter's correlation is `internal/eval_harness/ai_agent.go:250`,
which sends `SessionID: chainID` for the EVAL path, with the matching sessions row written by
`cmd/ailang/observatory_writer.go:42` / `eval_benchmark_agent.go:436`. The mission loop's own quorum
reviewer calls — the ones that produced iter-190's OpenRouter spend — are made outside
`eval_harness` and set no correlation at all, so no `session.id` arrives and there is nothing for M1
to resolve. M3 supplies the missing mechanism: pin the iteration's chain id in the post
(`IterationPost.ChainID` is now honoured), use it as the OpenRouter `session_id`, and register the
sessions row. Small, but it is what makes the sprint's headline query true for missions.

**2. Node attribution has no column.** Several nodes dual-writing into one remote store are
distinguishable only by `source_ref` (`mission:<name>/iter-<N>`). Deliberately not co-opting
`workspace_id` (it means something else and is a filter other tools join on). If it becomes needed,
the precedent is the quota bucket's free-text encoding in `agent_id`.

**3. Collaboration-hub re-baseline** (Mark asked for this as a SEPARATE thread):
`design_docs/planned/v1_1_0/global-collaboration-hub.md` reads as "not started" while at least three
of its six freeze items are resolved in shipped code (`internal/storage.Backends`, the Firestore
stores, `AILANG_TOPIC_PREFIX`). Re-baseline before writing anything new — it will likely shrink
materially.

**4. `ailang messages` cloud-first.** Local and cloud inboxes hold different populations — ~20
internal loop messages local, ~55 external (`mcp-public`, package feedback) in cloud, neither visible
to the other.

## Traps that cost time — all four still live

**1. Two functions carry an identical chain-extraction block.** `convertLogToSpan` (~line 445) and
`convertSpan` (~line 693) in `otlp_receiver.go`. The first M1 patch went into the logs path while
**Broadcast exports traces**. Always confirm which function you edited.

**2. Deployed observatories are FIRESTORE, not SQLite.** Both `ailang-dashboard` and
`ailang-dev-dashboard` run `AILANG_STORAGE=gcp`. `internal/observatory` migrations run only from the
SQLite paths and silently do nothing to dev or prod. See `.claude/rules/cloud-endpoints.md`. This is
why M3's `UpdateStageEvalAssessment` had to be implemented for Firestore, not just SQLite.

**3. `make test` is NARROWER than CI.** `test-nightly-classifier`, `verify-examples`,
`check-file-sizes`, `check-boundaries`, `check-changelog`, `check-skills`, `check-golden-drift`,
`test-regression-guards`, `verify-no-shim` are separate CI steps.

**4. `dev` is shared, and staging an explicit path is NOT sufficient.** Commit `088176104` swept a
concurrent agent's in-flight edit to `.claude/skills/mission-control/SKILL.md` and lost this
session's own edit to the same file — the live mission-control iteration rewrites that skill while it
runs, and `git add <path>` stages whatever the file holds at that moment, not what you wrote. For
files the loop touches (`SKILL.md` above all): edit, **grep the file to confirm your text is there**,
`git add`, commit, then **grep `git show HEAD:<path>`** — all in one shot. Recovered in `e4c45eb4f`.
