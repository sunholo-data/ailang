## Problem Statement

VER001 (toolchain-skew, `cmd/ailang/check_skew.go`) warns when the nearest `ailang.lock` was
generated by a different release than the running binary, and tells the user:

> Fix: regenerate the lock with `ailang lock` (accept the newer stdlib), or install the
> `<lock version>` toolchain to match.

That advice is a no-op. Running `ailang lock` on a package whose dependencies still resolve
the same prints `✓ Generated ailang.lock (N packages)` and leaves the file **byte-identical**
(`ailang_version`, `generated_at`, `generator` unchanged; only the mtime moves), so VER001
fires again on every subsequent check. The only step that actually clears the warning is
`rm ailang.lock && ailang lock` — which the warning never names.

**Root cause (two features, each correct alone, contradictory together):**

1. **v0.54.7 lock determinism** (stapledon workarounds doc, decision D2): on unchanged
   resolution, `preserveLockGeneration` (`cmd/ailang/pkg_lock_preserve.go:26`) copies the
   committed lock's *entire* generation metadata block — `GeneratedAt`, `Generator`,
   `AILANGVersion` — into the freshly resolved lock, so `ailang lock && git diff --exit-code`
   is clean in CI. `LockDrift` (`internal/pkg/lockcheck.go`) compares packages only and
   ignores metadata, so a toolchain bump alone is never "drift" and the old header survives
   every re-lock.
2. **VER001** (`cmd/ailang/check_skew.go:78-98`, newer): reads that same `AILANGVersion`
   field, compares release cores against the binary, and advises `ailang lock` — the one
   command D2 guarantees will *not* refresh the field it is complaining about.

**Repro (reporter, v0.56.1 binary, sunholo-data/ailang-packages `packages/observe` at b0ac7fd):**
lock written by v0.54.18, dependencies unchanged:

```
$ ailang lock && git diff --quiet ailang.lock && echo clean
✓ Generated ailang.lock (1 packages)
clean
$ ailang check --relax-modules lightcone.ail
WARNING VER001 (toolchain-skew): ailang.lock was generated by ailang v0.54.18, but this binary is v0.56.1.
  ... Fix: regenerate the lock with `ailang lock` ...
```

**Current State:**
- Bug still present at tree HEAD (v0.60.2, commit 05c860a lineage): `preserveLockGeneration`
  unconditionally preserves the metadata block on drift-free resolution (verified by reading
  `cmd/ailang/pkg_lock_preserve.go:26-33`).
- The existing test `TestPkgLockPreservesMetadata` (`cmd/ailang/pkg_lock_preserve_test.go`)
  actively asserts the byte-identity that causes this — the two features were never tested
  against each other.

**Impact:**
- Every package consumer (human or agent) who upgrades the toolchain and follows VER001's
  advice hits a dead end: the command "succeeds", the warning persists, and there is no hint
  that `rm` is required. For an unattended agent this is an infinite loop of
  warn → follow advice → warn.
- VER001 exists precisely to explain confusing cross-version type errors (e.g. the
  `string vs NetError` std/net skew that motivated it); its remedy being broken undermines
  the diagnostic it anchors.

## Goals

**Primary Goal:** Make VER001's stated remedy true: running `ailang lock` refreshes the lock
header exactly when VER001 would fire — and never otherwise.

**Success Metrics:**
1. On the reporter's repro shape (lock `v0.54.18`, binary newer, unchanged resolution),
   `ailang lock` rewrites the header (`ailang_version`, `generator`, `generated_at` now the
   running binary's) and the next `ailang check` prints no VER001.
2. Consecutive `ailang lock` runs under the *same* release core on unchanged resolution are
   still byte-identical (the v0.54.7 W3 CI contract survives, narrowed to same-toolchain).
3. A mechanical property test pins the invariant: `skewWarning(target, V) != ""` ⟺ the next
   `ailang lock` refreshes the header, over a version matrix.
4. All existing lock tests, including `TestPkgLockPreservesMetadata`, stay green unchanged.

## Solution Design

### Overview

One gate, one place. `preserveLockGeneration` currently preserves the previous lock's
metadata unconditionally on drift-free resolution. Give it the running binary's version and
make preservation conditional: preserve **iff** there is no drift **and** no decidable
toolchain skew. On skew, do nothing — the freshly built `LockFile` (which
`pkgLockCommand` already stamped with the current `Version`, generator string, and
`time.Now()`) is saved as-is, refreshing the header. No changes to `internal/pkg/`, the
lock format, resolution, or `--check`.

### Architecture

The invariant this design installs, and its two existing halves:

```
VER001 fires (skewWarning != "")
  ⟺ releaseCore(lock.AILANGVersion) and releaseCore(binaryVersion) are both non-empty and differ
  ⟺ (after this change) the next `ailang lock` saves a freshly stamped header
  ⟺ the next `ailang check` after that re-lock prints no VER001
```

**Components:**
1. **`preserveLockGeneration(previous, expected, binVersion)`** (`cmd/ailang/pkg_lock_preserve.go`):
   after the existing drift guard, add the skew guard — if
   `releaseCore(previous.AILANGVersion)` and `releaseCore(binVersion)` are both non-empty and
   unequal, return early (fresh stamp). Otherwise preserve the three fields as today.
   `releaseCore` already lives in the same `main` package (`cmd/ailang/check_skew.go`) — no new
   helper, no import cycle.
2. **Call sites** (`cmd/ailang/pkg_commands.go`, two: the empty-dependencies early path and
   the resolved path): pass `Version` as `binVersion`.
3. **Operator feedback**: when a drift-free re-lock refreshes a skewed header, print one
   informational line (e.g. `→ Refreshed ailang.lock toolchain stamp v0.54.18 → v0.56.1`)
   so the one-time diff is explained at the moment it is created. Exact wording is a
   deferred decision.

### Example 2: CI contract, unchanged for a pinned toolchain

A repo pinned to one release core, manifest untouched:

Only when the CI toolchain's release core differs from the lock's does the header rewrite —
once — surfacing the skew as a reviewable diff instead of a permanent warning.

### Example 3: Dev builds stay quiet

`go run`/`go test` builds carry `Version = "dev"` (no release core,
`internal/version/version.go:21`): no refresh, no churn, no VER001 — the same no-silent-guess

## Testing Strategy

**Unit tests:**
- `preserveLockGeneration` matrix (drift-free): same core → all three fields preserved;
  decidable skew → none preserved; either side lacking a release core → preserved
- The property test asserting `skewWarning(target, V) != ""` ⟺ refresh, for the same matrix
  (this is the regression lock for the bug class "advice names a step that doesn't work")

**Integration tests:**
- E2E re-lock: on-disk lock `v0.54.18`, `pkgLockCommand` under a temporarily overridden
  `Version` (package var; save/restore via `t.Cleanup`) → file bytes changed,
  `AILANGVersion` == override; second run byte-identical; `warnToolchainSkew` on the
  refreshed dir returns "" (`skewWarning` is pure and unit-testable — call it directly)
- Existing tests must pass **unmodified**: `TestPkgLockPreservesMetadata`,
  `TestPkgLockInvalidPreviousLock`, `check_skew_test.go`

**Manual testing:**
- Clone sunholo-data/ailang-packages at `packages/observe` (b0ac7fd), run `ailang lock`,
  confirm `git diff` shows only the 3 header lines, re-run `ailang check` → no VER001

## Non-Goals

**Not attempted in this feature:**
- **`pkg.EnsureLock` (the `ailang install` path, `internal/pkg/bin.go:116`)** — it returns
  early when a lock exists without re-resolving at all; a committed registry package's lock
  is a pure function of its pinned manifest and must not be restamped by installation.
  VER001's remedy is `ailang lock` in the package directory, which this fix makes work.
- **`ailang lock --check` reporting skew as drift** — `--check` is the CI gate; a contributor
  toolchain differing from the lock's must not fail CI resolution checks. VER001 already
  covers awareness.
- **A `--refresh`/`--force` flag or `rm` advice in VER001** — rejected (D3): new command
  routes count against the simplicity gates, and `rm` is a destructive, Windows-unfriendly
  instruction for a header refresh.
- **Changing VER001's wording** — after the fix, the existing wording is true. Only the
  refresh-notice line is added.
- **Lock format changes** — `ailang.lock/v1` schema and `LockDrift` semantics untouched.
