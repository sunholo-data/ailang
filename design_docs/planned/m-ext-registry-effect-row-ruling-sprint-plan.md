# Sprint Plan: Extension-Registry Effect-Row Compat Ruling

## Summary

Implement the approved compatibility ruling for `ailang generate-extension-registry`: retain the manifest `[effects].max` ceiling as the generated dispatch row, emit it canonically, validate every registered package's locked effects against it, and document the artifact's bound semantics.

**Duration:** 2 days  
**Estimated size:** ~500 LOC (implementation, tests, golden updates, and docs)  
**Dependencies:** Approved design document `design_docs/planned/m-ext-registry-effect-row-ruling.md`; no external dependency  
**Risk level:** Medium — the code change is localized, but it changes generated bytes and adds a new generation-time rejection path  
**Issue:** sunholo-data/ailang#800

## Current Status Analysis

- AILANG is at v0.42.0 on `coordinator/task-2f00aff7` (`fc0d4c90`).
- `effectRowFromManifest` currently preserves declaration order and the generated header does not explain that the row is a ceiling.
- `extRegistryGenCommand` already resolves every extension through `ailang.lock`; each `pkg.LockedPackage` already exposes its declared `Effects`, so validation needs no package loading or type-checking.
- Existing generator tests and `cmd/ailang/testdata/ext_registry_gen/two_packages.ail.golden` provide the correct regression surface.
- The seven-day history contains planning work only, so this estimate uses the design's one-day implementation estimate plus a full day of test, migration, and verification buffer rather than an unsupported LOC/day claim.

## Scope and Technical Approach

The implementation remains a manifest-plus-lockfile-to-text transformation:

1. Canonicalize a copy of `[effects].max` before rendering; never mutate parsed manifest state.
2. Compare each registered locked package's effect set with the manifest ceiling while packages are resolved. Report the package and out-of-ceiling effects deterministically.
3. Render a generated comment that explicitly calls the row the manifest ceiling and a superset bound.
4. Pin byte determinism, validation failure behavior, AILANG row-order compatibility, and documentation.

Out of scope: inferring performed effects, loading or type-checking extension packages during generation, per-extension effect rows, lockfile schema changes, and forced regeneration of existing external artifacts.

## Proposed Milestones

### M1: Canonical effect-row rendering

**Goal:** Make generated bytes independent of `[effects].max` declaration order while retaining the same effect set and historical empty-section default.  
**Estimated:** 35 LOC implementation + 85 LOC tests = 120 LOC  
**Duration:** 0.35 day  
**Files:** `cmd/ailang/ext_registry_gen.go`, `cmd/ailang/ext_registry_gen_test.go`

**Tasks:**

- Sort a defensive copy of non-empty manifest effects in `effectRowFromManifest`.
- Update the existing effect-row expectation to canonical order.
- Add a paired-manifest test proving different declaration orders generate byte-identical output.
- Retain and test the sorted historical fallback `Env, FS`.

**Acceptance criteria:**

- [ ] `effectRowFromManifest([]string{"IO", "Env", "FS"})` returns `Env, FS, IO` without mutating its input.
- [ ] Two manifests with the same effect set in different orders generate byte-identical files.
- [ ] Empty or omitted `[effects].max` continues to emit `Env, FS`.
- [ ] Focused generator tests pass.

**Risk:** Duplicate effects could render duplicate labels if malformed input reaches the generator. Mitigation: preserve manifest validation semantics; do not silently change list-to-set validation policy in this sprint.

### M2: Locked-package ceiling validation

**Goal:** Fail generation at the producer when a registered extension declares an effect outside the host ceiling.  
**Estimated:** 55 LOC implementation + 115 LOC tests = 170 LOC  
**Duration:** 0.65 day  
**Dependencies:** M1  
**Files:** `cmd/ailang/ext_registry_gen.go`, `cmd/ailang/ext_registry_gen_test.go`

**Tasks:**

- Add a small set-comparison helper over the manifest ceiling and `pkg.LockedPackage.Effects`.
- Validate the exact locked package returned by `FindPackage` inside the existing extension-resolution loop.
- Return a deterministic error naming the extension and sorted effects that exceed the ceiling.
- Cover compliant, violating, multiple-violation, and version-qualified extension references.

**Acceptance criteria:**

- [ ] An extension whose locked effects are a subset of the ceiling generates normally.
- [ ] An extension with any out-of-ceiling effect fails before template execution or file replacement.
- [ ] The error names the package, offending effect(s), and manifest `[effects].max` ceiling.
- [ ] Multiple offending effects are reported in stable sorted order.
- [ ] No package loader or type-checker is introduced into the generator path.

**Risk:** The historical omitted-section fallback and the validation ceiling could diverge. Mitigation: derive both rendering and comparison from one canonical effective-ceiling helper and pin omission behavior in tests.

### M3: Generated contract and regeneration proofs

**Goal:** Make the ceiling semantics explicit in the generated artifact and prove clean regeneration plus effect-row order compatibility.  
**Estimated:** 25 LOC implementation/golden + 125 LOC tests/fixture = 150 LOC  
**Duration:** 0.65 day  
**Dependencies:** M1, M2  
**Files:** `cmd/ailang/ext_registry_gen.go`, `cmd/ailang/ext_registry_gen_test.go`, `cmd/ailang/testdata/ext_registry_gen/two_packages.ail.golden` (and a focused `.ail` fixture only if needed)

**Tasks:**

- Add the approved manifest-ceiling/superset line to `extRegistryTemplate`.
- Update the golden file for the one-time canonical reordering and header change.
- Add an idempotent regeneration test that generates twice and compares exact bytes.
- Add a focused `ailang check` compatibility test/fixture showing reordered equal effect sets type-check identically.

**Acceptance criteria:**

- [ ] Generated header states that the dispatch row is the manifest `[effects]` ceiling and a superset of registered extensions.
- [ ] Running generation twice from unchanged inputs produces exactly identical bytes.
- [ ] The golden output matches the canonical header and row.
- [ ] `ailang check` accepts equivalent rows whose labels appear in different orders.
- [ ] The complete `cmd/ailang` generator test subset passes without skips.

**Risk:** A subprocess-based compatibility test could accidentally use a stale binary. Mitigation: prefer an in-process parser/type-check fixture; if a CLI test is necessary, build the test binary explicitly and fail rather than skip.

## Success Metrics

- Same ceiling set in any declaration order produces byte-identical generated output.
- Unchanged regeneration produces an empty diff.
- Every registered extension's locked effects are checked before output replacement.
- Error output identifies the violating package and stable offending-effect list.
- Generated source and user guide both distinguish a ceiling bound from performed effects.
- Existing generated registries remain type-compatible; only canonical order and the explanatory comment change.
- No new package metadata, loader dependency, or language feature is introduced.
